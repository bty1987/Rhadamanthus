# 电子合同业务逻辑功能总结（fl-sign 反哺）

> **状态**：反哺参考（2026-10-25），只读知识搬运，不含开发任务。
> **来源**：`D:\Git\fl-sign` 深读（方林新微服务线的电子合同中心，生产现行，e签宝 V3 全套对接）。
> **定位**：老系统（本系统）电子签已完成多厂商架构并按"模板级迁移"推广中（见 `01-方案设计/电子签扩展方案.md`、根目录《电子签e签宝真实合同试点方案》《电子签全公司推广切换方案》）。fl-sign 是另一条线上更重的"合同中心"实现——本文把它的业务模型全量总结过来，供推广收尾、能力补齐与两条线未来对齐时参照。
> **红线**：fl-sign 的 appId/secret 等配置值一律不入文档（配置项 key 名可引）。

---

## 一、一句话定位

fl-sign 把"合同"从业务模块里抽出来做成了**独立的合同中心微服务**：模板（含版本链与控件库）、实例（十态状态机）、签署主体（企业/经办人/印章三层+岗位授权）、撤销与作废（解约）全套自治，业务方只凭 `biz_module + biz_id` 关联发起合同——与老系统"合同逻辑散在各业务 ServiceImpl + 厂商适配层"是两种形态。

## 二、总体结构

- 模块：`fl-sign-api`（Feign 契约：5 个 RPC 接口 + 全部枚举/DTO，供其它方林服务依赖）+ `fl-sign-biz`（实现，Spring Boot 3 / MyBatis-Plus / Nacos / RabbitMQ）。
- 12 个 Controller：合同分类 / 合同类型 / 控件字段库 / 控件组 / 模板 / 实例 / 回调 / 企业主体 / 主体岗位 / 企业印章 / 主体经办人 / 个人印章。
- 5 个 RPC 接口：ContractInstanceApi（创建/流转/撤销/详情）、ContractTemplateApi（详情/分页）、OrgSubjectApi（认证发起/刷新）、OrgSubjectStampApi、PsnSubjectStampApi——其它服务不碰合同细节，只调这五类能力。
- 外部依赖：fl-resource（文件/OSS）、fl-serial（合同编号序列）、fl-user（员工）、fl-cms（元素字段库=模板变量来源）。
- MQ：单队列 `fl-sign`，专用于 e签宝回调异步消费。
- 业务关联：`sign_contract_instance.biz_module`（业务模块名）+ `biz_id`（业务单据ID）——合同中心不知道订单/供应商是什么，只知道"替谁发的"。老系统对照：合同 PO 直接挂在各业务表上，这是两条线最根本的形态差异。
- 配置：Nacos `fl-sign.yaml`，业务 key 仅 `fanglin.esign.key / fanglin.esign.secret / fanglin.esign.host`（e签宝开放平台凭证，host=smlopenapi.esign.cn）。回调走网关 `/admin-api/sign/esign/callback/**`，以 URI 元数据 `requireLogin=false` 放行（老系统回调 esignAuthCallback 的对应物）。

## 三、领域模型（15 张表，前缀 `sign_`）

| 表 | 内容 | 关键字段/说明 |
|---|---|---|
| contract_category | 合同分类目录 | orgId + name + type（供应商合作/补充协议/客户装修合同） |
| contract_type | 业务侧合同类型 | 可配**发起方式多选**（模板发起/直接发起）、**审批流ID**、**可签岗位**（子表 type_position）——类型即管控策略 |
| contract_template | 合同模板 | 双指针：`esignTemplateId`（e签宝侧当前生效模板）+ `recordCurrentId`（生效制作记录）/`recordLatestId`（最新草稿记录） |
| contract_template_record | 模板制作记录 | **版本链**：一模板多条记录，expand 存签署方配置(2~3方)、e签宝制作/编辑/预览 URL 与时效、底稿 PDF OSS 路径 |
| contract_component_group / component_field | 控件组/控件字段库 | 控件组同步到 e签宝自定义控件组；字段映射 fl-cms 元素字段，分三组：供应商信息/公司主体信息/自定义 |
| contract_template_component | 模板控件实例 | 模板制作完成后从 e签宝**回读落库**：控件类型、所属签署方、页码/X/Y/required |
| contract_instance | 合同实例 | biz_module+bizId、signWay（电子签/补录）、esignFlowId、esignRescissionFlowId（解约流程）、状态、expand（签署方快照/变量值/各阶段文件） |
| org_subject | 签约主体（我方法人） | orgId→主体两层；统一社会信用代码+法人三要素；authStatus（实名）与 authStatus（授权）**双状态**；authFlowId；authUrl 30 天有效 |
| org_subject_transactor | 主体经办人 | 实名认证状态、authFlowId（人脸认证） |
| org_subject_stamp | 企业印章 | e签宝 sealId、类型（模板章/图片章）、业务用途（公章/合同章/人事章/财务章/法人章）、**autoStamp 开关**、审核状态、章图 OSS 路径 |
| org_subject_stamp_position | 印章-岗位授权 | 限定哪些组织架构岗位可用该章 |
| org_subject_position | 主体-岗位 | 主体可用的岗位范围 |
| psn_subject_stamp | 个人印章 | 同企业印章流程，多 esignAccountId |

**关键设计**：
1. **模板版本链**：模板编辑永远产生新 Record；Record 完成时把同模板其它未失效 Record 全部置 CLOSED，`recordCurrentId` 指向生效版——"最新草稿"与"生效版本"分离，停用模板再编辑自动开新版本线。
2. **主体三层模型**：主体（实名+授权）→ 经办人（自然人，人脸实名）→ 印章（审核制+岗位授权+自动章开关），多公司多主体各管各的章。老系统对照：`signet` 表一司一章+keyword，推广到 53 家公司时 fl-sign 这套分层值得参照（§八）。
3. **实例快照**：发起时把签署方配置、模板变量定义快照进 expand——后续模板改版不影响在途合同。

## 四、状态机与枚举全集

### 4.1 合同实例十态（核心状态机）

```
INIT(10草稿) → READY(20待签署) → DOING(30签署中) → SUCCESS(90已完成)
                    DOING → REVOKE_DOING(32撤销中) ──回调撤销──→ INIT（可重新发起）
                    DOING → INVALID_DOING(92作废中) ──回调解约──→ INVALID(99已作废)
                    回调拒签 → REJECTED(34) / 过期 → EXPIRED(36) / 其余异常 → FAILURE(40)
守卫：canEdit=[INIT,READY]；canRevoke=[DOING]
     canRollback=[DOING,REVOKE_DOING,REJECTED,EXPIRED,FAILURE] → 一律回 INIT 重发起
```

- INIT→READY：回填模板变量 → e签宝按 docTemplate 生成正式合同文件 → 转存 OSS → 附件上传。
- READY→DOING：按模板签章区（SEAL_AREA 控件按甲/乙/丙方分组）+ 附件关键字定位生成签署域 → 创建签署流，**顺序签由签署方 sortValue 控制**。
- SUCCESS 回调时同步下载**已签终稿+附件**转存 OSS——终稿归档是回调链路的一环，不是人工动作。

### 4.2 模板与制作记录

- 模板：INIT(草稿)→DONE(制作完成)→ENABLED(启用)→DISABLED(停用)；仅停用态可再编辑（开新版本）。
- Record：INIT→DOING(制作中)→DONE(完成)/CLOSED(失效)；canEdit=[INIT,DOING]。

### 4.3 印章/认证状态

- 企业/个人印章五态：待审核→审核通过/拒绝→已启用/已停用（e签宝 sealStatus 映射：1已启用/2待审核/3不通过/4挂起）。
- 主体：未认证→认证中→已认证/失败（实名），未授权→授权中→已授权（授权）——**实名与授权是两件事**。
- 经办人：待认证→认证中→已完成/失败。

### 4.4 签署方形态（Side × SubjectType × ProxyType 组合）

- Side：甲/乙/丙三方；SubjectType：个人客户/企业客户/供应商/装修公司；一份合同 **2~3 个签署方**。
- ProxyType 决定"谁代表该方落笔"：本人（个人）/ 认证法人（企业/供应商）/ 装修公司三种——**自动落章**（凭 esignOrgId 静默签）/ 签约主体法人手签 / 合同发起人以经办人身份手签。
- 印章指定：签署方配置带 esignSealId → 签署域 assignedSealId，落章位置、用哪枚章都在发起时定死。
- 补录通道：signWay 区分**电子签/补录**——线下已签的合同也登记进合同中心，只走状态不走 e签宝流。

## 五、核心业务流程

### 5.1 控件库与模板制作

1. 控件组/字段在本地维护（分组：供应商信息/公司主体信息/自定义），**同步到 e签宝自定义控件组**，拿回控件组/控件 ID——保证多模板控件口径统一。
2. 范本 PDF 两步式上传（取 file-upload-url → PUT 流 + Content-MD5 → 轮询 3 次确认）。
3. 调"创建模板制作链接"，**在 e签宝托管编辑页完成制作**（本地不画坐标）→ 拿 docTemplateId。
4. e签宝回调"模板制作完成" → 回读控件明细，与本地字段库 diff 落库（含页码/坐标）→ 底稿 PDF 转存 OSS → Record=DONE、模板=DONE，旧版本全 CLOSED。
5. URL 时效管理：制作链 24h（提前 1h 判失效）、预览链 30min——过期必须重取，不能落库长期用。

### 5.2 实例发起与签署

```
add(模板+biz关联+签署方快照) → 编辑(变量值/附件) → READY(填充生成正式文件)
→ DOING(创建签署流:顺序签+签章域+指定印章) → 签署方收短链手签 / 装企方静默签
→ 回调 SIGN_FLOW_COMPLETE → 终态+终稿下载归档
```

- 签署链接按"流程详情里找到当前操作人的 psnId"再取长/短链——每个签署人各取各的。
- 附件（如报价单）随主文件进同一签署流，签章位置用 `/v3/files/{fileId}/keyword-positions` 按关键字检索——与老系统 keyword 落章同一思路。

### 5.3 撤销与作废（解约）——老系统完全没有的能力

- **撤销**（签的过程中终止）：仅签署中可撤 → 本地先置"撤销中" → 调 e签宝 revoke → 回调撤销完成 → 回到 INIT，可改后重发起。
- **作废/解约**（签完之后作废）：查流程详情找装企经办人 → 以"装修公司+经办人"身份对已签文件发起 **initiate-rescission** → 回调解约成功 → 状态=已作废，解约文件单独归档（invalidFileInfoList+invalidTime）。
- 装修合同"签完又解约"是真实高频场景（退单/重签），老系统目前没有对应模型，这条链路可直接借鉴。

### 5.4 企业主体/经办人/印章

- 主体实名+授权一次办理：org-auth-url 带**授权范围参数**（未实名先引导实名再引导授权，一次 H5 完成）→ 回调 AUTH_PASS/AUTHORIZE_FINISH 落"已认证+已授权"；另有主动 refresh 按 authFlowId 查询兜底（回调丢失时用）。
- 经办人：psn-auth-url 默认**人脸认证**。
- 印章：模板章（在线生成）/图片章（上传图→e签宝审核→回调审核结果→确认后下载章图存 OSS）；**syncEsign 定期拉 e签宝章列表对账**（防两边不一致）；autoStamp 开关控制该章能否静默签；岗位授权表限定用章人群。

### 5.5 个人印章

与企业章同构（模板/图片两型+审核回调+对账+下载落 OSS），删除时同步删 e签宝侧。

## 六、e签宝 V3 对接清单（实际在调用的接口）

**鉴权**：Header 四件套——App-Id / Auth-Mode:Signature / Ca-Timestamp / Ca-Signature（HmacSHA256+Base64，POST/PUT 附 body 的 Content-MD5）。自研纯 HTTP 层，无 SDK 依赖（与老系统 ESignElecsignServiceImpl 同款做法）。

| 域 | 接口 |
|---|---|
| 文件 | file-upload-url、文件详情轮询、keyword-positions（关键字定位）、create-by-doc-template（模板填充）、file-key（印章图） |
| 模板 | 制作链接、编辑链接、预览链接、模板详情回读 |
| 签署 | create-by-file（建流）、sign-url、flow/detail、revoke、file-download-url、initiate-rescission（解约） |
| 实名 | org-auth-url、psn-auth-url、auth-flow/{id}（状态查询）、identity-info/org-info |
| 印章 | org-seals create-by-template/create-by-image、org-seal-info、org-own-seal-list、org-seal(删)；personal 同构一套 |
| 控件 | custom-components / custom-component-group 增删改查同步 |

**回调体系**（`POST /esign/callback` → action 白名单校验 → 包成 MQ 消息 → 消费者分发）：

| action | 含义 | 处理 |
|---|---|---|
| 1 实名认证通过 | 主体/经办人认证结果 | 置已认证、回填 esignOrgId |
| 5 授权完成 | 印章授权 | 同上复用 |
| 7 印章审核 | 图片章审核结果 | 通过→可用并下载章图；拒绝→记原因 |
| 9 模板制作完成 | 托管编辑页保存 | 回读控件落库、Record=DONE、版本链翻转 |
| 21 签署流程结束 | signFlowStatus: 2完成/3撤销/5过期/7拒签 | SUCCESS(+终稿下载)/回退INIT/EXPIRED/REJECTED/FAILURE |
| 23 解约成功 | 已签文件作废完成 | 状态=已作废+解约文件归档 |

幂等不靠去重表：靠"反查业务单 + 状态机 statusFrom 比对"，重复回调天然被状态守卫挡掉；e签宝侧重试即 MQ 重投。

## 七、与老系统电子签的差异对照（借鉴点）

| 维度 | 老系统现状 | fl-sign | 可借鉴点 |
|---|---|---|---|
| 签署完成推进 | **人工点"已签"确认** | 回调驱动状态机+终稿自动下载归档 | 推广方案已计划"卡流巡检兜底"；正解是吃 SIGN_FLOW_COMPLETE 推状态，人工确认降为异常兜底 |
| 模板 | e签宝控制台维护+模板级路由（已拍板） | 托管制作页+版本链+控件回读落库 | 模板级迁移路线不变；版本链思想可用于 data.contract 行的"新旧并存"治理 |
| 解约/作废 | 无 | initiate-rescission 全流程+回调 | **最大缺口**。退单重签场景可按 §5.3 补 |
| 签署主体 | signet 一司一章+keyword | 主体→经办人→印章三层+岗位授权+对账 | 53 家公司逐家办授权（推广 D2）时，主体/印章分层与 syncEsign 对账值得抄 |
| 企业自动落章 | 仅应用主体免授权；其余公司 org-auth-url+manage_org_resource 授权（已实测） | 装企方 autoSign=true+指定印章，但 ProxyType.autoSign 恒 false——**写了未启用** | 两线互证：静默签能力=应用主体免授权+印章授权两条路；启用与否是业务开关 |
| 回调安全 | esignAuthCallback，未见验签 | action 白名单+MQ 异步，**也无验签** | 两线都欠验签，应统一补（对照官方向回调内含签名/自行对账） |
| 合同编号 | 各业务单据自有编号 | 序列服务"HD"（降级"HT"+时间戳） | 合同中心化时的编号规范 |
| 撤销后复用 | — | 撤销回 INIT 可改可重发，不浪费已填数据 | 流程体验细节 |

## 八、风险与反面教材（fl-sign 实读发现，引以为戒）

1. **回调接口无验签**——只校验 action 白名单，伪造回调可推状态机；两线都应补。
2. **自动落章"写了没接通"**：SignerProxyTypeEnum.autoSign() 恒 false，AUTO 路径实际不可达——照抄状态机时要逐路径核对可达性，别只看枚举定义。
3. 经办人认证后 esignTransactorId 未回写（字段预留但断链）；解约发起人却依赖"流程详情里的经办人"——数据链有隐性缺口。
4. dev/local 配置文件明文 DB 口令与 e签宝密钥入库（生产走 Nacos）——与老系统 EncryptConfigLoader 加密方向一致，别倒退。
5. 制作/预览链接强时效（24h/30min），任何"存链接以后用"的设计都会踩过期坑。
6. 巨型 ServiceImpl 反模式依旧（实例服务单文件过大，状态迁移逻辑靠独立 Helper 才救回来）——老系统改造时应把状态机独立成 Helper/策略，不进主流程方法。

## 九、对老系统的落地建议（不排期，供决策）

1. **归档环节先接回调**：推广方案阶段 1 的"卡流巡检兜底"落地时，同步让 e签宝 SIGN_FLOW_COMPLETE 回调推合同状态+触发终稿下载，"员工点已签"降级为兜底——这是 fl-sign 已验证的形态，改动只在 esign 包+回调入口。
2. **解约能力单独立项**：按 §5.3 模型补"已签合同作废"，退单/重签场景闭环。
3. **印章授权台账**：53 家公司逐家授权（D2）进行中，台账字段建议对齐 fl-sign 主体表（authFlowId/授权状态/有效期），授权一次永久有效但要可查可催。
4. **回调验签两线统一**：fl-sign 与本系统同一短板，修一处沉淀方案，另一处复制。
5. **两条线长期关系**：fl-sign 是"合同中心"形态（业务方只给 bizModule+bizId），老系统是"嵌入式"形态（合同挂业务表）。若未来收敛，方向应是业务表保留、合同执行细节向合同中心靠——本总结即收敛时的对照基线。

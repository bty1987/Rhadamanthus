# 工费/材料验证相关变更记录体系设计

> 版本 v1.1(实施设计版) | 2026-11-12 | 状态:方案评审稿(未落码,仅 DDL 草案附件已落盘)
> 目标:对影响工费与材料验证逻辑的 7 类变更建立统一留痕,支持按单追查、按人追责、按时间还原,为后续管控(审批/权限)或开放(放行留痕)提供数据基础。
> 拍板记录(2026-11-12):①单表 ②qfid 换绑走受控接口 ③记录不清理 ④不要审批,只要记录(一期纯留痕,二期管控作废)

## 一、背景与问题

工费验证(normriceitem 确认链 + 工费浮动上限校验)与材料验证(normooditem 有效行合计 + 辅材-定材归集)的输入数据,散布在 7 个变更点上,当前**全部无任何变更记录**——改了什么、谁改的、何时改的、改前是什么,库里无迹可查。出问题(工费超发、材料验证合计异常、报价与定额对不上)时只能靠结果倒猜。

## 三、设计方案

### 3.1 总体形态:一张统一变更记录表

7 个变更点跨 quotation/data/construction 三库,但业务上是同一主题("影响工费/材料验证的变更"),且追查场景的主视角是**按装修单/按报价单看完整时间线**——分域表会让追查要跨三张表拼。故采用**单表**,落 `quotation` 库(7 点中 5 点主数据在 quotation;表无跨库 FK 约束,记录 orderId/qid 字符串关联即可)。

**表草案 `quotation.normchanerecord`(定额变更记录)**:

| 列 | 类型 | 说明 |
|---|---|---|
| ncrId | bigint PK AUTO | 主键 |
| type | tinyint | 变更类型枚举(见 3.2) |
| changeType | tinyint | 动作:1添加/2修改/3删除/4绑定/5解绑/6启用/7禁用 |
| orderId | varchar(50) | 装修单号(追查主视角,索引) |
| qid | bigint | 报价单 id(索引,可空——纯档案类变更如定材浮动额无 qid) |
| refId | bigint | 关联业务 id(按 type 语义:arId/ngid/normtion.nid/aid/qfid/noods.nid 等,索引) |
| refNo | varchar(100) | 关联业务可读标识(增减单号/定材名/辅材名/节点名,便于列表直读) |
| beforeValue | varchar(500) | 变更前关键值(文本,"字段: 值"分号拼接或 JSON) |
| afterValue | varchar(500) | 变更后关键值 |
| comment | varchar(500) | 补充说明(如连带影响:"删除增减单连带删下定材3行") |
| operater | varchar(32) | 操作人 userId |
| operateTime | timestamp | 操作时间 |
| company | int | 租户(索引) |

索引:(orderId),(qid),(refId),(company,operateTime)。

**记录格式约定**(仿 constructionrecord 但结构化两列):beforeValue/afterValue 只记**验证相关的关键字段**,不整行快照——如定材浮动额记 `浮动量: 100`;下定材删除记 `定材: XX型号, 定额数量: 3, 库房数量: 5`;节点工费记 `工费浮动: 5000, 浮动增量上限: 8000`。

### 3.2 变更类型枚举(type)与写入点矩阵

| type | 语义 | 写入点(Service 层,均 @Transactional 内) | 动作 | before/after 内容 |
|---|---|---|---|---|

| 2 | 增减项删除 | deleteAddReduceByArId@722 / deleteAddReduceItem@282(明细级) | 删除 | 被删单/项摘要+**连带影响**(连带删下定材 N 行@809) |
| 3 | 定材浮动额变更 | NoodsServiceImpl.updateNoods@113(**需改为先 get 旧值再覆盖**,当前 copyProperties 不读旧值) | 修改 | `浮动量: 旧→新`(surplus 变了才记,避免 copyProperties 全量噪音) |
| 4 | 节点工费浮动变更 | ConstructionScheduleServiceImpl.updateConstructionScheduleForNorm@204 | 修改 | `工费浮动: 旧→新, 增量上限: 旧→新`;seiya A20251208 旁路@817 同步接入 |
| 5 | 下定材添加/删除 | NormoodItemServiceImpl.addNormoodItem@73 / deleteNormoodItem@165;makeNormtion 重建事件记 type=5 changeType=禁用+添加 汇总一条(防重算噪音) | 添加/删除 | 定材名/定额数量/库房数量;删除记行快照 |

### 3.3 写入模式与噪音控制

- **显式 save**(仿 constructionrecord):每个写入点在事务内一行 `normchanerecordDao.save(new NormchanerecordPO().init(type, changeType, ...))`,新 PO 带 builder 风格 init(参照 DecorationOperatePO)。
- **不搞 AOP 统一拦截**:actionLog 已覆盖接口级;业务 diff(旧值→新值)必须读旧值才能写,只有业务代码内做得准。
- **噪音控制三则**:①updateNoods/copyProperties 类"全量覆盖"入口必须**先比对后记录**(值没变不记);②makeNormtion 整单重算合并为一条汇总记录(附影响行数),不逐行刷;③before/after 只记验证关键字段,非验证字段(如打印次数)不记。
- **大表零侵入**:normriceitem(2400万行)/normooditem 千万级**主表零改动**,记录全在新表,不加重主表写放大。

### 3.4 管控与开放分层(本期只做"开放+留痕",管控留接口)

- **本期(留痕)**:7 点全部保持现状可操作(开放),全量落记录。运维 SQL 换绑 qfid 例外——见下。
- **qfid 换绑治理**(第 7 点的关键缺口):当前换绑无代码入口纯运维 SQL,无法留痕。两选一:
  - **推荐**:新增受控接口 `updateQuotationItemForQfid`(权限收紧到管理员,通过 operation 表 through=0 授权控制),换绑走代码入口自动留痕;存量运维 SQL 场景迁移到该接口;
  - 备选:维持 SQL 换绑,规范要求 DBA 执行时配套 INSERT 记录行(不可靠,不推荐)。
- **管控(二期可选,本期不落)**:type=3(定材浮动额)/type=4(工费浮动)这类直接改变验证阈值的变更,可升级为"变更需审批"(仿 normriceitem 确认链或 approval 模块);记录表已含全部字段,升级不需要再改表。

### 3.5 查询与展示

- **后端**:按 orderId / qid / refId 三维查询 + 按操作人/时间段/类型过滤(分页,接口命名按规范:`pageNormchanerecordByOrderId` 等,落码时按 METHOD_NAMING_CONVENTION 细化)。
- **前端**:装修单详情页与定额单页各加"变更记录"入口(popup 时间线列表:时间/操作人/类型/内容);第一期只读。
- **追查场景示例**:工费超发 → 按 orderId 查时间线 → 看到"节点工费浮动: 3000→8000, 某人, 某时" → 定位阈值被谁放大;材料验证对不上 → 看"下定材删除"记录与 makeNormtion 重算记录。

## 五、风险与注意事项

1. **copyProperties 全量覆盖点**(updateNoods)必须先读旧值——这是唯一的"改造写法"而不只是"加埋点"的点。
2. **makeNormtion 重算噪音**:报价每次变更都触发整单 disable+重建,若逐行记录会把记录表刷爆——必须合并为单条汇总(type=5,comment 带"重算影响 N 行")。
3. **事务边界**:记录 save 放业务事务内(同 constructionrecord 模式),不学 actionLog 的 REQUIRES_NEW——变更记录与业务同生共死,业务回滚记录也回滚,避免"有记录无变更"。
4. **seiya 旁路**:节点工费浮动有 A20251208ServiceImpl 同逻辑旁路(外部同步接口),埋点必须两处都挂,否则外部同步改值不留痕。
5. **表名与 catalog**:统一表落 quotation 库;quotationrecord 在 customer 库是历史特例,不仿效。
6. **命名规范**:新接口/方法落码时按 METHOD_NAMING_CONVENTION(本方案内暂用占位名)。
7. **SQL 规范**:DDL 落 sqls/quotation/(序号接现有),幂等 CREATE TABLE IF NOT EXISTS+注释头(用途/前置/回滚/验证)。

### 7.5 🔴 部署序与跨模块依赖(同款教训=approval-information-jar-missing-incident)

埋点横跨 **4 个模块**(quotation/data/construction/seiya),而 data/construction/seiya 的埋点需注入 quotation 包的 NormChangeRecordDao——运行时四 jar 同一 WEB-INF/lib 无编译问题,但**漏发任何一个 jar,对应模块埋点触发即 NoClassDefFoundError(线上表现 110000)**:

```
部署序: 60号DDL → 61号operation SQL(可选,受控接口授权)
   → 四 jar 同批: fanglin-quotation + fanglin-data + fanglin-construction + fanglin-seiya
   → 前端(normchanerecord.html/js + 两个入口按钮)
```

- 兼容性:DDL 先行(旧 jar 不写新表,零影响);漏发某 jar 的唯一后果=该模块变更不落记录或该模块写操作炸 110000,故**四 jar 缺一不可,必须同批**

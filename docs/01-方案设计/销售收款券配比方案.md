> 模块：payment（收款/配比明细新表）× decoration（decorationactivityitem 券行消耗）× decoration 增项域（saleScale 计算链）

> 日期：2026-11-07
> 上游：《阶梯抽奖活动方案.md》（type=30 券的发放侧；本文档为其下游讨论清单第 1 项"券的用途"的定案）

## 一、需求与业务流（用户拍板 6 点）

阶梯活动券（type=30、state=2 已领）在**销售收款**时选择使用——页面/链路（2026-11-07 用户纠正定案）：

- **页面=`js/payment/salesPayment.js` 收款弹窗（collectModal）**，收款时决定；**无审批环节**（collect 提交成功后前端自动确认，与装修款/预付款一致）；
- 收款类型限 **2 定金 / 3 补款 / 8 不退定金**（`collectType` 白名单）；
- 服务端=`api.payment.collectSalesPayment`（单笔）/`collectSalesPayments`（批量）→ `SalesPaymentServiceImpl.collectSalesPayment`（status→PAIDFOR）——**券消耗挂此处**；

1. **券抵扣收款金额（拍板 A）**：应收 X、用券抵 Y、实收现金 X−Y；
2. **被抵的 Y 计入配比基数（拍板 计入）**：券抵扣视同已收，参与主材额度配比计算（影响 saleTotal/materialPaidup）；
3. **完成收款（status=1 已付）时券转"使用"（拍板 已付）**：`decorationactivityitem` 状态从已领(2) → **消耗(7, STATUS_CONSUME_INT，状态机选型)** + 状态流水；
4. **收款作废不回滚券（拍板 不做）**：券保持 7 消耗终态、明细保留计入；
5. **配比明细表通用化（拍板 推荐+冗余）**：来源类型枚举可扩、字段冗余（orderId/company/来源行 id），为未来其他配比来源（场外款明细化等）预留；
6. **选券范围限本装修单（拍板 装修单范围内）**：数据源=`decorationactivityitem` 该 orderId + type=30 + state=2。

## 二、既有"配比"体系考古（区分两个概念，避免混淆）

| 体系 | 表/字段 | 语义 | 与本方案关系 |
| --- | --- | --- | --- |
| **销售配比（saleScale）✅本方案落点** | saleTotal 计算链（`DecorationAdditionServiceImpl.updateDecorationForSaleScale`）→ `DecorationMidpackPO.materialPaidup`（整装 Holonomy 对应） | 销售侧计入主材配比的总额：**销售收款 + 预付款主材余额 + 场外款(仅 isScale=需配比)**，现算无明细——"糊涂账"所在 | 正统词根 saleScale，新表 `decoration.decorationscaledetail` 归 decoration 域 |
| **款项比例方案** | `data.paymentscale` / `data.paymentscaleitem`（NERP 收款按 psid 拆 decorationpayment，A20261025Service） | 🔴**给 decorationpayment 拆分款项使用的，不是配比**（用户明确纠正）——新表禁止蹭 `payscale` 词根 | ❌无关，命名上注意区分 |
| **场外款配比标记** | `OalesPO.isScale`（0需配比/1不需配比） | 场外款是否计入配比基数——**同构先例**（isScale 命名对齐） | 明细表 isScale 命名对齐；场外款存量不重做明细 |

主材额度 = 工程总额 × 主材配比（Midpack/Holonomy），materialPaidup = 销售侧已计入配比部分。

## 三、数据结构（新表 + 券面值修正）

### 3.1 配比明细表 `decoration.decorationscaledetail`（新增）

🔴归属 decoration 库（用户确认）：命名对齐 decoration 域 `decorationXXX` 表族；配比消费点（saleScale 链/materialPaidup）全在 decoration 增项域，未来其他来源（sales/payment 库的场外款、收款来源）也集中写本表——配比明细单库单表可查。

🔴命名：**不用 `payscale` 词根**——`data.paymentscale`（款项比例方案）是给 **decorationpayment 拆分款项**用的，与配比无关；"销售配比"的正统词根是 **`saleScale`**（`DecorationVO.saleScale` 字段 + `updateDecorationForSaleScale` 配比计算链），新表对齐。

```sql
CREATE TABLE IF NOT EXISTS decoration.decorationscaledetail (
  psdId BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  spid BIGINT NULL COMMENT '销售收款单 payment.salespayment.spid(单笔收款必填,批量可空——批量=同一装修单多笔收款行,配比按orderId汇总)')
  orderId VARCHAR(20) NOT NULL COMMENT '装修单号(冗余,跨收款单汇总)',
  sourceType TINYINT NOT NULL COMMENT '来源类型 1=阶梯券(枚举可扩:场外款等)',
  sourceId BIGINT NULL COMMENT '来源行id(通用:券=daiId)',
  daiId BIGINT NULL COMMENT '券行 decorationactivityitem.daiId(券来源;UNIQUE 一券一用并发兜底)',
  asid BIGINT NULL COMMENT '券奖品(冗余,展示/对账)',
  money BIGINT NOT NULL COMMENT '计入金额(厘)=券面值',
  isScale TINYINT NOT NULL COMMENT '是否计入配比 0计入 1不计入(对齐OalesPO命名)',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '明细状态 0有效(预留作废标记,一期不启用)',
  creater INT NULL COMMENT '操作人uid',
  createTime DATETIME NULL,
  comment VARCHAR(200) NULL,
  PRIMARY KEY (psdId),
  UNIQUE KEY uk_daiId (daiId),
  KEY idx_pid (pid),
  KEY idx_orderId (orderId)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='收款配比明细';
```

冗余字段（决策 5）：orderId/company 语义与 sourceType/sourceId 通用列——未来其他来源（场外款明细化、收款类来源）接入时扩 sourceType 枚举即可，表结构不动。

### 3.2 type=30 券面值修正（推翻原 money=0 拍板）

券要参与配比金额必须有面值：阶梯券落行时 **`money = activityitem.money`（配置面值，厘）**——一二三等=不同面值券。券族 `{0,10,20}` 不含 30，面值仍不进 couponCut/thingCut 金额口径 ✓。

## 3.5 页面融合与原有券共存（🔴谨慎部分，用户特别提醒）

**salesPayment.js 收款弹窗已有"原有券处理"**：`couponCheckbox/couponDiv` 开关 + `couponType`（typeahead 券种，源自 receiptType 字典 TYPE_COUPON）+ `couponVal`（手填金额）+ `couponAdd` → `paymentUtils.addCounpon()` 加券列表 → `paramCoupon()` 读列表金额进 `realPayment` 凑齐应收 → 落 `salesReceipt.coupon/couponInfo`（"券名|金额#"字符串拼接档）。

**共存规则（阶梯券=独立区，原字典券零改动）**：

| 项 | 原有字典券 | 新增阶梯券 |
| --- | --- | --- |
| 选择方式 | couponType 选券种 + couponVal 手填金额 | typeahead 选本单 type=30/state=2 券行，**金额=券面值只读** |
| 数据源 | receiptType 字典（TYPE_COUPON） | `decorationactivityitem` type=30/state=2/本单 |
| 提交 | `paramCoupon` → `salesReceipt.coupon/couponInfo` 字符串档 | `daiIds[i]` 参数（照 ptids 模式）→ `decorationscaledetail` 明细表 |
| 金额 | 计入 realPayment 凑齐应收 | 计入 realPayment 凑齐应收（同一校验式追加变量） |
| 状态流转 | 无（纯字符串档） | 完成收款 → 券行 2→7 消耗 + 状态流水 |
| 共存 | **两者可同时存在于一笔收款**，金额各自累加进 realPayment | |

**提交链改动（唯一原有逻辑侵入点）**：`collect()` 的 `realPayment` 计算式追加阶梯券金额变量（`paramLadderCoupon()` 新增，照 `paramCoupon` 样式）；不选阶梯券时行为与现状完全一致。

**批量收款（2026-11-07 修正：支持）**：`collectSalesPayments` 批量的前提=多笔收款行**同属一个装修单**（同一 sid/orderId）——`daiIds` 对整批生效（所选券均为该单的券），逐明细落行（每 daiId 一行，spid 可空）；服务端守卫=校验批内 spid 的 orderId 一致且与券 orderId 一致，不一致拒绝。

## 四、业务流程与状态机

```
【收款选券】创建/编辑销售收款单（选择本单阶梯券：type=30 AND state=2 AND orderId 匹配）
   └─ 落配比明细行：pid + daiId + money(券面值) + isScale(默认计入)
      + 防重守卫：该 daiId 已存在有效明细 → 150 段新码拒绝（一券一收款）
【完成收款】收款确认链 status 0→1 已付（PaymentServiceImpl 多处 setStatus(PAID)，实现时统一挂点）
   └─ 对该 pid 的有效明细逐条：券行 state 2→7 消耗（STATUS_CONSUME_INT）+ DecorationActivityRecord 流水
      （券不涉及 awardstock 扣减——阶梯发放时已扣）
【配比计算】updateDecorationForSaleScale 计算链追加：
   saleTotal += SUM(decorationscaledetail.money WHERE orderId=? AND isScale=计入 AND status=0)
   （被券抵的 Y 视同已收参与配比 → 主材额度口径）
【作废】收款作废(status=3) → 不回滚（决策 4）：券保持 7 消耗、明细保留计入
```

**收款单金额口径（推荐，待确认）**：收款单 `balance` 录**实收现金 X−Y**（前端录入口径），券抵的 Y 只存在于明细——现有 `amountSalesPayment`（SUM balance）零改动，配比基数 = balance + 券明细计入额 = X ✓ 对现有链路零侵入。

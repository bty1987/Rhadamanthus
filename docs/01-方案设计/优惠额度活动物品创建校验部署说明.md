## 一、部署范围与影响面

| 对象 | 动作 | 影响面 |
| --- | --- | --- |
| decoration 库 | 新表 `decorationactivitycost`（SQL 22）+ constant 字典 10/11/12（SQL 23） | 零数据变更、零存量表修改 |
| ERP 四节点 jar（decoration / approval / information 模块） | 重打部署 | 尽力而为哨兵：未配置=跳过校验（额度物品照常创建），fl-yy 异常=跳过校验放行；**唯一拦截=接口明确 usable=false**；非额度物品全流程零影响 |
| 前端 | `decoration4activity.js` / `decoration4detail.js` | 仅"优惠额度类物品"交互变化（提交带 aiid、type 传配置值、分组映射） |
| 外部 | fl-sync/fl-yy 签名入口（已上线）+ `erp_project_sync` 密钥 | ERP 为调用方，不要求外部变更 |

## 二、前置条件（缺一不可）

1. fl-sync/fl-yy 签名入口版本已部署：`POST /open-api/sync/cycx/discount-quota/validate` 可用（Apifox 已实测，现算约 3.4s）；
2. 各环境 Redis Hash `api_signature_app` 的 `erp_project_sync` 密钥在位（复用既有，禁止覆盖/重生成）；
3. **向运维索取** `erp_project_sync` 的 appSecret（测试/正式各一套）——这是 ERP 侧唯一新增的外部依赖项。

## 三、部署步骤（严格按序）

### 步骤 1：SQL（decoration 库 + communion 库，一次执行）

🔴 两件均为幂等可重跑；**22 必须先于 jar**（`DecorationActivityCostPO` 映射该表，硬依赖）。

### 步骤 2：communion.systemconfig 配置（数据库表，改库即生效免重启）

配置读 `communion.systemconfig`（全局 key、company=0、group='cost'），按环境执行：

```sql
INSERT INTO communion.systemconfig (`group`, `key`, value, company, comment)
SELECT 'cost', 'cost.validate.url', 'https://daily-gateway.fanglin.vip/open-api/sync/cycx/discount-quota/validate', 0, '优惠额度校验接口地址(正式=gateway.fanglin.vip)'
FROM DUAL WHERE NOT EXISTS (SELECT 1 FROM communion.systemconfig WHERE `key` = 'cost.validate.url');

INSERT INTO communion.systemconfig (`group`, `key`, value, company, comment)
SELECT 'cost', 'cost.app.secret', '<erp_project_sync 对应环境密钥>', 0, '优惠额度签名密钥(向运维索取,禁止覆盖既有值)'
FROM DUAL WHERE NOT EXISTS (SELECT 1 FROM communion.systemconfig WHERE `key` = 'cost.app.secret');
```

不配置 = 跳过校验（额度物品照常创建，log.warn 留痕），其余功能零影响——可用于灰度，且灰度期间不存在"配置缺一半被卡"的问题；密钥轮换只改表值，改库即生效免重启。

### 步骤 5：冒烟（daily 先行）

见方案文档第九节测试要点，最小集：

1. **回归**：不配密钥状态（或先验证再配）——添加普通活动物品全流程正常；
2. **配置后**：添加额度物品 → 校验通过落行，`decoration.decorationactivitycost` 出现缓存行（money/balance/toplimit 存厘、daiId 关联、无 staffCode 列）；
3. **拦截**：构造额度不足 → 140108（reason 透传文案）——这是唯一拦截条件；
4. **放行**：fl-yy 停机/错密钥/删配置 → 额度物品照常创建（应用日志 log.error/log.warn 留痕），无缓存行；
4. **金额口径**：添加额度物品后装修单 `couponCut/thingCut/factPrice` 不变（type 白名单天然排除）；
5. **审批路径**：申请含额度物品的活动 → 审批通过落行 type=10/11/12、合并金额一次校验、cost 行逐明细落档。

## 四、回滚

1. jar 回退即恢复原逻辑（前端可不回退——新前端对老 jar 的增量字段 aiid 会被忽略，额度物品 type 传配置值由服务端按 asid 反查兜底覆盖）；
2. 已落的 cost 行数据无害留存，可选 `DROP TABLE decoration.decorationactivitycost`（仅限数据可弃时）；
3. 字典 6 行可选 `DELETE`（对应方案文档 23 号 SQL 头部回滚语句）。

## 五、已知限制与注意事项

1. **validate 只校验不扣减**：跨单额度防不住（员工可在多单各添加、每次校验都过）——额度治理闭环待 fl-yy 使用/扣减流程上线，届时 `checkBeforeCreate` 一层对接演进；
2. **尽力而为语义**：fl-yy 不可用/配置缺失期间额度物品放行创建（仅日志留痕）——接受"外挂离线时无前置拦截"换取业务连续性；
3. **现算耗时**：validate 为实时规则计算（实测 3.4s），校验位于事务内写库之前，异常即跳过放行（唯一拦截 usable=false 时事务回滚零脏数据）；批量审批多明细已做合并金额一次校验；
4. **签名时钟**：timestamp 与服务器时差 ≤30 秒——四节点 NTP 需正常（时钟偏移只会导致跳过校验放行，不会阻塞业务）；
5. **密钥安全**：appSecret 只进 sysconfig/服务端，不进前端不进日志；fl-yy 侧轮换密钥时 ERP sysconfig 同步更新（未同步期间跳过校验放行）；
6. **审批明细展示瑕疵**：decoration4activity.js 申领弹窗（apply 路径）提交 type 仍按组硬编码——审批落行时服务端按 asid 反查覆盖为 10/11/12，仅审批明细表展示语义为"券/物品/红包"而非"优惠额度*"，不影响校验与落行正确性；
6. **type 语义**：10/11/12 对齐 `ActivityItemPO` 既有 0=券/1=物品/2=红包（额度-券/额度-物品/额度-红包），前端归组按"数值-10 同组"。

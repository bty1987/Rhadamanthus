# 优惠额度活动物品创建校验方案

> 模块：decoration / information / approval（ERP 侧）× fl-yy 优惠额度对外校验接口
> 关联文档：《优惠额度对外接口文档》（fl-sync 签名入口，`POST /open-api/sync/cycx/discount-quota/validate`，**ERP 恢复直接调用**）
> 状态：已实施（2026-10-25 五次修订=尽力而为语义定稿并完成代码落地，待编译部署；额度为现算、数据同步不可行，回到接口调用+轻量化；**唯一拦截条件=接口明确 usable=false(140108)，未配置/请求异常一律跳过校验放行**）
> 日期：2026-10-25

---

## 一、背景与目标

fl-yy 维护优惠额度池（品牌业绩净累计/工程额度/来源规则/到期日/使用日期），ERP 原生无此领域。ERP 侧需求：**设计师在装修单上添加"优惠额度"类活动物品（`decoration.decorationactivityitem`）之前校验资格，通过才允许创建**，使额度使用在 ERP 装修单上留痕。

**对接方式（2026-10-25 四次修订定案）**：fl-yy 额度为**现算**（无静态池表），数据同步方案不可行，**回到接口调用**。轻量化原则：砍展示查询/进程内缓存/冗余错误码/冗余配置键，ERP 侧收敛为"**一个类 + 两行调用 + 一张缓存表 + 两个配置键**"；审批路径合并金额一次校验（N 次现算 → 1 次）。**尽力而为语义：唯一拦截条件=接口明确 usable=false（140108），未配置/请求异常一律跳过校验放行创建**。

涉及两条既有落行路径，**都校验**：

| 路径 | 前端 | Action | 落行 Service |
| --- | --- | --- | --- |
| 直接添加 | `decoration4activity.js` 添加弹窗 | `addDecorationActivityItem.do`（现有，不动） | `DecorationActivityItemServiceImpl.addDecorationActivityItem` |
| 审批申请 | `decoration4detail.js` 活动信息节点 | 审批模块（现有，不动） | `ApprovalDecorationActivityServiceImpl.approveForDecorationActivity`（审批通过落行时刻） |

## 三、类型扩展：`information.activityitem.type` 10/11/12

### 3.1 语义

| type | 含义 | 前端分组 | 落行 type |
| --- | --- | --- | --- |
| 10 | 优惠额度-券 | coupons 组（映射 -10, 对齐 type=0 券归组） | 10 |
| 11 | 优惠额度-物品 | things 组（映射 -10, 对齐 type=1 物品归组） | 11 |
| 12 | 优惠额度-红包 | papers 组（映射 -10, 对齐 type=2 红包归组） | 12 |

常量定义在配置端 `ActivityItemPO`：`TYPE_COST_COUPON_INT = 10` / `TYPE_COST_THING_INT = 11` / `TYPE_COST_REDPACKAGE_INT = 12`（对齐既有 0=券/1=物品/2=红包 语义），判定条件统一为 `type >= 10`。

### 3.2 为什么金额口径天然不受影响（自洽性论证）

两条落行路径的金额口径都是 **type 白名单式**，10/11/12 天然被排除：

- 审批落行 `ApprovalDecorationActivityServiceImpl`：couponCut/thingCut 累计分支条件为 `type∈{0}` / `type∈{1}` 且 isPayment=CAL，10/11/12 两分支均不命中；
- DAO 汇总 `DecorationActivityItemDaoImpl.amountDecorationActivityItem`：SQL 显式 `type = 0` / `type = 1` 过滤。

因此额度行落 10/11/12 后，`couponCut/thingCut/factPrice` 纹丝不动——"原有逻辑不变"零代码实现。

### 3.3 现状 type 链路（改造依据）

- **直接添加**（decoration4activity.js:587-625）：先 `queryActivityItemByAiid` 取配置（money 单价/asid），但提交的 `decorationActivityItem.type` 是**弹窗手选分类**，money 传配置单价——落行 money=单价、num=数量，总额=单价×数量在统计时相乘，口径一致；
- **审批路径**（decoration4detail.js:545-605）：type 是**前端按分组硬编码**（things→1 / coupons→0 / papers→2），money 从 typename 属性解析，随审批明细（`ApprovalDecorationActivityItemPO` 有 type/money/num/asid，无 aiid）透传落行。

两处 type 都是前端说了算 → 必须服务端按配置覆盖（见 5.4）。

## 四、总体链路

```
设计师添加/申请优惠额度物品（选配置 type≥10 的物品 + 数量，无金额输入框、不展示额度）
        │
        ▼
Service 落行方法开头（写库前）── DecorationActivityCost.checkBeforeCreate(...) 一行调用（5.10）
        │  ①识别：直接添加 activityItemDao.get(aiid) / 审批 queryActivityItemByAsid(asid)
        │     配置 type ∈ {10,11,12} → 额度类；非额度类走原逻辑零改动
        │  ②金额：amount(元) = money(厘) × num ÷ 10⁶（额度类单价按整数元配置，无精度损失）
        │  ③签名调用（4 Header，appId=erp_project_sync）：POST cost.validate.url
        │     { staffCode: 登录人userId / 审批发起人, orderId, amount }——现算约 3.4s
        │     审批路径：同单同员工多明细合并金额一次校验（5.3）
        ▼
├── code=0 && usable=true  → 落行（type 服务端覆盖为配置值 10/11/12）+ 落 cost 缓存行(5.5) + 状态流水
├── code=0 && usable=false → FLException(140108, 接口 reason 原文透传)，事务回滚零脏数据【唯一拦截条件】
└── 未配置/网络/超时/签名/非0 → log 留痕后跳过校验放行创建（type 仍按配置覆盖，无缓存行）
```

HTTP 调用位于 `@Transactional` 方法**最前、任何写库之前**：校验不过即抛，事务回滚无脏数据；现算实测 3.4s，事务内等待可接受（写库前只读阶段）。

## 五、后端改动

### 5.1 校验客户端（新建，唯一新类）

`src/com/fanglin/decoration/utils/DecorationActivityCost.java`（类名用户定义），判定 + 签名调用 + 落缓存档一体，**无缓存、无展示查询**（轻量裁撤，见 5.9）。照 `com.fanglin.esign.utils.EsignClient` 样式（HttpURLConnection，connect 5s / read 10s，fastjson 解析）：

- `checkBeforeCreate(orderId, userId, activityItemPO, money, num)`：判定 `type >= 10` → 额度类则组装 `staffCode=userId / orderId / amount`（元，=money×num÷10⁶）调用 validate；返回响应快照（availableAmount/perOrderLimit）供落 cost 缓存行；
- **签名（4 Header，fl-sync 硬要求）**：`appId`（固定 `erp_project_sync`，硬编码常量）、`timestamp`（Unix 毫秒，与服务器时差 ≤30 秒）、`nonce`（SecureRandom 16 字节 hex，60 秒防重）、`sign = SHA256_HEX("#" + rawBody + "##" + "appId=..&nonce=..&timestamp=.." + "###" + appSecret)`——无 Query 参数故 queryString 空串；**rawBody 签名与发送同一份**（fastjson `toJSONString` 一次，两处共用）；密钥 `cost.app.secret` 按环境配置；
- 尽力而为语义：usable=false → 140108（msg=接口 `reason` 原文透传，**唯一拦截**）；未配置/网络/超时/签名失败/非 0 → log 留痕后返回 null，调用方跳过校验放行创建（type 仍按配置覆盖）。

### 5.2 直接添加路径挂点

`DecorationActivityItemServiceImpl.addDecorationActivityItem` 方法开头（取奖品之前），判定/校验/缓存落档**全部封装为一行 `decorationActivityCost.checkBeforeCreate(...)` 调用**（见 5.10），其内部逻辑：

1. 识别：`aiid` 优先（新前端必传）→ `activityItemDao.get(aiid)`；未传时按 `asid` 反查 `queryActivityItemByAsid` 兜底（兼容存量前端）；**反查不到配置视为非额度类走原逻辑**（不抛错，保存量兼容）；
2. `activityItemPO.getType() >= 10` → 额度类：尽力而为签名调用 validate（staffCode=入参 userId，现算约 3.4s；未配置/请求异常 → 跳过放行）；
3. 通过后落行：`decorationActivityItemPO.setType(activityItemPO.getType())` **覆盖前端手选分类** + `content` 人读摘要，其余照旧（state=INIT、isPayment 硬编码 UNCAL）；物品行 save 后落 cost 缓存行（携带 daiId，company 取 `decoration.company`）。

### 5.3 审批落行挂点

`ApprovalDecorationActivityServiceImpl.approveForDecorationActivity` 落行循环内、save 之前，同 5.2 封装为一行 `checkBeforeCreate` 调用（见 5.10），其内部逻辑：

1. 预扫明细：逐条 `queryActivityItemByAsid(明细.asid)` 反查配置，反查不到视为非额度类；
2. `type >= 10` → 额度类：staffCode 取 `approvalPO.getSender().getUserId()`，**同单同员工多明细合并金额一次校验**（amount=Σ money×num÷10⁶，N 次现算 → 1 次；通过后逐明细落行，总额已验无需逐条再调）；
3. 通过后 `decorationActivityItemPO.setType(反查type)` 覆盖明细透传值 + `content` 人读摘要；明细 save 后逐条落 cost 缓存行（company 取 `decoration.company`）。

校验挂**审批通过的落行时刻**而非申请时刻（申请到落行有时差，额度以落行为准）。

### 5.4 识别信任链

| 路径 | 识别方式 | 为什么 |
| --- | --- | --- |
| 直接添加 | VO 加 `aiid`（Java 字段，非 DDL；BeanUtil VO→PO 无此属性自动跳过）→ `activityItemDao.get(aiid)` 直查 | 前端已有 aiid（typeahead 绑定值），直查无歧义 |
| 审批 | 新增 DAO 方法 `queryActivityItemByAsid(long asid)` 反查，多条取第一条 | 明细无 aiid 且不加列；同奖品跨活动按"type 配置一致"业务约定 |

前端传的 type 一律不作触发依据（改客户端传 0 即可绕过校验），仅作展示。

### 5.5 校验结果缓存落库（新表 `decoration.decorationactivitycost`）

**定位=缓存**：校验通过落行时同事务落一条 cost 行，缓存本次接口响应快照（balance/toplimit/使用额度）。**三不**：不展示（5.9 已裁撤）、不参与校验判定（校验永远实时调接口，缓存数据禁止作为判定依据）、系统逻辑不读（读场景仅人工排查与后续对账）。字段本地化：

| 对外字段 | 本地化 | 类型/单位 | 说明 |
| --- | --- | --- | --- |
| —（staffCode） | **不落** | — | ERP 对应词本是 userId，按拍板省略——操作人经 `decorationactivityitem.cuid` 追溯 |
| orderId | `orderId` | varchar | 装修单号（ERP 同名） |
| — | `daiId` | bigint | 关联 `decorationactivityitem.daiId`（同事务先落物品行后落 cost 行，必有值） |
| amount | `money` | int / 厘 | 本次使用额度（元×1000），全项目通用金额字段名 |
| availableAmount | `balance` | int / 厘 | 校验时点员工可用额度（取自接口响应快照），对齐 `WalletPO.balance`/`AdvancePaymentPO.balance` 先例 |
| perOrderLimit | `toplimit` | int / 厘 | 校验时点单笔上限（取自接口响应快照），对齐 `WorkerBalancePO.toplimit`/`ProtationCostPO.toplimit` 先例 |
| reasonCode | **不落** | — | 仅校验通过落行，全表隐含 OK |
| companyShortName | `company`（int） | — | 落 `decoration.company` 数字公司；简称不落（关联即得） |
| —（校验时间） | `createTime` | datetime | — |

主键 `dacId`（对齐 daiId/darId 命名族）。DDL（`sqls/decoration/22_decorationactivitycost_create.sql`，**先于 jar 硬依赖**——PO 映射新表）：

```sql
CREATE TABLE IF NOT EXISTS decoration.decorationactivitycost (
  dacId BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  orderId VARCHAR(20) NOT NULL COMMENT '装修单号',
  daiId BIGINT NOT NULL COMMENT '活动物品行 decorationactivityitem.daiId',
  money INT NOT NULL COMMENT '本次使用额度(厘)',
  balance INT NULL COMMENT '校验时点可用额度(厘)',
  toplimit INT NULL COMMENT '校验时点单笔上限(厘)',
  company INT NULL COMMENT '公司',
  createTime DATETIME NULL COMMENT '校验时间',
  PRIMARY KEY (dacId),
  KEY idx_orderId (orderId),
  KEY idx_daiId (daiId)
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='装修活动优惠额度校验记录';
```

`content` 人读摘要保留在额度物品行上（仅实际校验通过时写入）；`comment` JSON 快照废弃（由本表取代）。缓存表只增不改：额度行落 state=0 后无核销/领取/退货动作，字段不会被后续流转覆盖；校验跳过（未配置/请求异常）时不落缓存行。

### 5.8 配置（2 键）

- `cost.validate.url`（测试=`https://daily-gateway.fanglin.vip/open-api/sync/cycx/discount-quota/validate`，正式=`https://gateway.fanglin.vip/open-api/sync/cycx/discount-quota/validate`）——未配置=跳过校验，额度物品照常创建（type 仍按配置覆盖），log.warn 留痕；
- `cost.app.secret`（`erp_project_sync` 应用既有密钥，测试/正式各一套，向运维索取，服务端存 Redis Hash `api_signature_app`，禁止覆盖/重生成）。

`appId` 固定 `erp_project_sync`，硬编码为类常量（接口文档明示固定值），不设配置键。两键任一未配置 = 跳过校验放行（不拦截）。

### 5.9 展示能力裁撤（轻量化）

原"弹窗展示可用额度/单笔上限 + 展示查询接口 + 进程内缓存"整体裁撤：额度为**现算**（实测 3.4s/次），为展示在每次开弹窗时调接口（或为此维护缓存）不成比例；`queryDecorationActivityCost` Action/Service 不再新建，前端弹窗不展示额度信息。产品后续要展示时另议数据源再定（当前定案不显示），加回不影响核心链路。

**命名说明**：本升级的业务域是 **decorationactivityitem 的创建校验**，方法/类命名锚定 `DecorationActivity` 前缀（归队模块内 `queryDecorationActivityItem`/`amountDecorationActivityItem` 既有方法家族），**词根统一 Cost（用户定义）**：校验客户端类 `DecorationActivityCost`（用户定义）、常量 `TYPE_COST_COUPON_INT/TYPE_COST_THING_INT/TYPE_COST_REDPACKAGE_INT`（宿主 `information.ActivityItemPO`，对齐既有 0=券/1=物品/2=红包）、配置键 `cost.validate.url`/`cost.app.secret`（沿用 `esign.orginfo.*` 点分风格）；缓存表 **`decorationactivitycost`**（用户定名）主键 `dacId` 对齐 daiId/darId 族，字段本地化对齐既有先例（`balance`←`WalletPO.balance`、`toplimit`←`WorkerBalancePO.toplimit`、`money` 全项目通用金额字段）。对外契约字段（staffCode/orderId/availableAmount/perOrderLimit）与 fl-yy 路径 `discount-quota` 为外部契约保持原文不动。

### 5.10 触发判定与解耦（系统/产品视角）

ERP 原生没有"额度"领域概念——本验证是 fl-yy 领域能力的**前置哨兵**，设计目标=可整体摘除的外挂，不把额度逻辑种进核心。

**三层判定，全部配置/字典驱动，核心代码零硬编码**：

| 层 | 开关 | 不满足时 |
| --- | --- | --- |
| 产品层 | 活动物品字典是否开放 10/11/12（constant 字典 + 运营是否配置此类物品） | 永不触发，相关代码为死代码 |
| 物品层 | 配置端 `activityitem.type >= 10`（Service 读配置判定，唯一触发点） | 按普通物品落行，零感知 |
| 系统层 | `cost.validate.url`/`cost.app.secret` 已配置 | 跳过校验放行创建（log.warn 留痕，type 仍按配置覆盖）——外挂不在场时业务照走 |

**耦合盘点与收敛**：ERP 对 fl-yy 零制品依赖（HTTP+JSON+2 个配置键），编译耦合仅"两条落行路径各一行调用"。收敛约定：

- 判定+签名调用+缓存落档全部封装在 `DecorationActivityCost.checkBeforeCreate(...)`，两条落行路径**各只留一行调用**（5.2/5.3 展开的步骤即该方法的内部实现）；返回"非额度类跳过 / 额度类通过（携带覆盖 type）/ 拒绝抛 140108-110"；
- 摘除成本 = 删一个类 + 删两行调用 + DROP cost 表 + 删字典行 + 删两个配置键；
- `decorationactivitycost` 表是 ERP 本地数据、不构成外部耦合，但列入整体摘除清单；
- **明确不做**：拦截器/策略框架抽象（为一次对接引入框架，违反项目简洁气质）；校验异步化（校验是同步前置条件，不通过不得创建）。

**演进视图**：当前=外挂哨兵（本方案）；未来出现完整利润模块时，额度成为利润域一等公民——`checkBeforeCreate` 一行调用改为利润域服务调用，`decorationactivitycost`/`decorationactivitycostpool` 并入利润账本，核心落行逻辑无需回改。

### 5.11 数据同步方案废止记录（现算不可同步）

2026-10-25 三次修订曾定"Python 每分钟同步 fl-yy 额度入本地快照表 `decorationactivitycostpool`"（userId/balance/toplimit/syncTime + `crond_activity_cost_sync.py` 每分钟 crontab）。**经确认 fl-yy 额度为现算**（品牌业绩/工程额度/规则在查询时实时计算，无静态池表可读），同步方案物理上不成立——本节留档作废，回退接口调用（5.1），pool 表与 Python 脚本不再出现在改动清单。

## 八、明确不做 / 已知缺口

1. **缓存不参与校验判定**：缓存（5.9）仅供展示"可用额度/上限"，落行前校验永远实时调用 validate，不存在缓存复用跳过校验；
2. **跨单额度防不住（已知缺口）**：validate 只校验不扣减，员工在 A/B 单各添加一笔、每次校验都过（额度池无感）。本方案闭环"资格校验 + 实时一致性"；真正闭环待 fl-yy 使用/扣减流程上线，届时演进为"ERP 落行后通知 fl-yy 扣减"或"先调 fl-yy 使用接口再落行"，落行代码不变；
3. **不涉及 140094**：额度行无核销逻辑；
4. **amountDecorationActivityItem 手动统计**（限 SIGNED/FINAL 单）不受影响：额度行 type 不在统计口径。

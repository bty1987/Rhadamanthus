# 主要模块 status/type 字段逐行混淆存储方案

> 2026-11-16 · 设计稿(未落码, 待拍板)
> 需求: 主要模块的 type/status 以随机化方式存库, 数值类型兼容现有 tinyint; 同一业务状态在不同行的存储值不同(如 decoration.decoration.status 0→102 只对某一单成立), 起到加密/混淆作用。

---

## 1. 目标与威胁模型

**目标**: 仅持有数据库(导出/只读账号/脱库)的人, 无法从 status/type 列直读业务状态, 也无法用简单统计直接还原语义。业务代码、前端、App(Ding/Wechat)、外部接口(NERP/金蝶/消息队列推送)的**行为与协议完全不变**。

**边界(明确不抗)**:
- 不抗拿到应用代码+密钥的人(拿到 `obf.codec.secret` 即可解);
- 不抗"已知明文+等值类聚类"对**检索列**的语义推断(见 §2, 数学上检索列必然暴露等值类; 但单行主列抗已知明文);
- 只覆盖枚举型数值列, 不是金额/姓名类列级加密。

**实测基线**(生产只读 RDS 实证, 2026-11-16):
- 目标列全部为 `tinyint(1)`(**有符号**, 合法域 0..127); `communion.customer.type` 与 `decoration.projectStatus` 为 `int(11)`, 默认排除在 tinyint 域外;
- 全项目 po/ 下名为 status/type/state 的字段 **305 个 / 221 个 PO**, `STATUS_/TYPE_/STATE_` 常量 793 个 / 137 文件;
- 新列名 `obfSalt` / `statusTag` 全库零冲突。

---

## 2. 核心矛盾: 逐行随机化 vs 等值检索 (为什么必须双列)

逐行随机化的定义本身就与 `WHERE status = 3` 这类等值检索矛盾: 同一逻辑值在各行存储值不同, SQL 就没有任何一个常量可以命中它。**这一点数学上不可两全**, 全库等值可检索加密(确定性加密)必然退化为"同值同存储", 即丧失逐行随机性。

因此方案采用**双列结构**, 把"可逆存储"与"可检索"拆开:

| 列 | 性质 | 用途 | 泄露什么 |
|---|---|---|---|
| `status` (原列) | 逐行乱序, 可逆 | 真实存储, 单行读写 | 无(单行看不出任何语义) |
| `statusTag` (新增) | 逐字段固定双射 τ | 等值检索/排序外所有 WHERE/GROUP BY | **等值类**: 两行 tag 相同=状态相同, 但不知道是哪个状态 |

这与项目已有先例同构: `company` 列 AES 加密存储, 查询前 decode 参数再比对密文(`CompanyServiceImpl:240`), 等值类同样是暴露的——区别只是本方案主列做到了**逐行不同**, 比 company 先例(同值同密文)更强。

**不支持的字段形态**: 位掩码字段(如 `otherStatus`, 走 `Restrictions.sqlRestriction("otherStatus & ?")` 位与查询)无法混淆(位运算会破坏双射结构), **一律排除**。

## 3. 总体架构 (五件套)

```
内存世界(Java/JSON/前端): 永远是逻辑值 0..8/20/30/32/33
        │ getStatus()/setStatus() 语义不变
        ▼
┌─ ObfEntityInterceptor (Hibernate, 唯一读写闸门) ─────────────┐
│  onLoad        : status = dec(存储值, rowKey)      ← 解码    │
│  onSave        : 存储值 = enc(logical, rowKey)     ← 编码    │
│  onFlushDirty  : currentState[]与previousState[]对称变换      │
└──────────────────────────────────────────────────────────┘
        │ DB 见到的: status=逐行乱序值, obfSalt=行密钥材料, statusTag=τ(logical)
        ▼
查询路径: WHERE status_tag = :τ(v)   ← 参数经 ObfCodec.tag() 折算
```

| 组件 | 位置 | 职责 |
|---|---|---|
| `ObfCodec` | `com.fanglin.utils` | 纯算法: `enc/dec/ns密钥/salt/tag/untag`, 静态方法, 无状态 |
| `obfSalt` 列 | 每张纳入表 | 行密钥材料, smallint, `0=明文直通`(安全网), 新行随机 1..65535 |
| `statusTag` 列 | **仅有查询点的字段**才加 | τ(logical), tinyint(1), 需要的字段建索引 |
| `ObfEntityInterceptor` | `com.fanglin.core.interceptor` | 读写透明化(§5), 挂 `sessionFactory` 的 `entityInterceptor` |
| `ObfRegistry` | `com.fanglin.core.interceptor` | 静态登记表: (实体类, 属性名) → {tag属性名?, 域上限}, 也是查询收口点的判定源 |

**PO 变更量**: 每个纳入 PO 加 2~3 行字段声明 + getter/setter(`obfSalt` 必加; 有查询点的字段再加 `statusTag`)。机械改动, 编译器兜底。常量类(`DecorationPO.STATUS_*` 等 793 个)与常量体系(constant 表 / CONSTANTS.md)**一个都不动**。

## 4. 编码算法规范

算法必须可双语言复刻(Java + Python 脚本工具), 规范如下:

```
namespace n  = "库名.表名.列名"          (如 "decoration.decoration.status")
salt s       = 1..65535 随机            (0 保留为"明文直通"语义)
rowKey K     = SHA-256(secret ‖ 0x00 ‖ n ‖ s 大端2字节) 取前 8 字节 (uint64)

enc(v, n, s):                                  # v ∈ [0, 127]
    8bit Feistel 4轮:  L=v>>4, R=v&15
    每轮: L,R = R, L ^ (F(K,r,R) & 15)        # F=splitmix64(K ^ r·G ^ R·G2), G为固定常数
    输出 y=(L<<4)|R  ∈ [0,255] 是 0..255 上的双射
    cycle-walk: while y > 127: y = feistel(y)  # 迭代收敛, 期望 2 次
    return y
dec(y, n, s) = enc 的逆(Feistel 逆向走轮)       # 同一行稳定且唯一

tag(v, n)   = τ_n(v):  同款 Feistel, key' = SHA-256(secret ‖ 0x01 ‖ n), 固定 salt=0
untag(t, n) = τ_n 的逆                          # GROUP BY 结果回译用
```

- **双射性**: Feistel 结构天然双射; cycle-walk 保持子域双射 → 迁移对账恒等式成立(§8);
- **逐行随机性**: rowKey 含每行 salt → 同一逻辑值在不同行(不同 salt)的存储值不同, 满足需求核心;
- **单行稳定性**: 同一行同一状态的存储值恒定(enc 确定性), 重复 save 不会漂移;
- **检索列无碰撞**: τ 是双射不是截断哈希——截断 8bit 哈希对 13 个状态值碰撞概率 ~28%, 不可用;
- **伪随机函数选 splitmix64 而非 HMAC**: 威胁模型是"防脱库者读语义", splitmix 密钥化后在 8bit 域上与 HMAC 的实际强度差异无意义(攻击者无密钥时只能蛮力 2^64), 而开销差三个数量级(每次转换 ~百 ns); 若日后要加密级强度, 只换 F 实现, 接口不动;
- **域上限**: tinyint(1) 有符号 → 域 0..127(现网全部状态值 ≤33, 合法); 若纳入 tinyint unsigned 列, 该字段域参数配 255 即可; int 列不纳入。

**密钥管理**: `obf.codec.secret` 放 `conf/sysconfig.properties`(应用服务器本地文件, 对齐 jdbc.properties 管理方式)。**严禁放 sysconfig DB 表**——被混淆对抗的正是能读库的人。三环境(dev/test/prod)各自独立密钥。密钥轮换 = 全表重写 job(机制同迁移, 日常用不到)。

## 5. 读写路径透明化 (Hibernate Interceptor)

选 Interceptor 而非两条被否掉的路:
- **getter/setter 内转换**: 可行(全项目 649 个 PO 实测 100% property access, 注解在 getter 上)但要把 221 个 PO 逐个改方法体, 散弹式修改 review 不可控;
- **UserType/CompositeUserType**: `nullSafeGet/Set` 拿不到行内其他列(盐/主键), 逐行键控不可行;
- **Interceptor 零 PO 方法侵入**, 一个类+一张登记表收口全项目, `ApplicationContext.xml` 的 sessionFactory 当前**无** `entityInterceptor` 属性(实测), 新增即可, 无冲突。

三个钩子的正确姿势:

```java
public class ObfEntityInterceptor extends EmptyInterceptor {
    // onLoad: state[] 由 DB 读出 → 对登记属性逐个 dec → Hibernate 用返回数组建实体
    public boolean onLoad(entity, id, state[], propertyNames[], types[]) {
        对每个登记属性 i:  state[i] = salt(state[盐位])==0 ? state[i]          // 明文直通
                                        : codec.dec(state[i], ns, salt);
        return true;  // state[] 被替换
    }
    // onSave: 新插入 → 若 obfSalt==0 先生成随机盐 → state[i] = enc(logical)
    //         实体内存字段保持逻辑值不动
    public boolean onSave(...) { ... }

    // onFlushDirty: 🔴 必须对 currentState[] 与 previousState[] 做对称变换
    //   current=实体内存(逻辑值)→enc;  previous=加载快照(逻辑值)→enc
    //   差分比较发生在"编码后 vs 编码后" → 没改状态就不会假脏
    //   若只变换 current, 每次任何 update 都会把 status 判为脏 → 每次多一条 UPDATE
    public boolean onFlushDirty(...) { ... }
}
```

**兼容性结论**(全部来自实测审计):
- 内存态恒为逻辑值 → 全项目 **912 处** `po.getStatus()` 判断、BeanUtil 复制、Struts JSON 序列化、Ding/Wechat 纯前端、messagecueuing payload 内嵌逻辑值、NERP 入向 Service 走 PO——**全部零改动**;
- 二级缓存/查询缓存(EhCache, 已开启): L2 缓存的是 onLoad 之后的解码态, 命中不经过 interceptor, 不会二次解码 ✓;
- detached PO 跨模块 `update()` 69 处: 内存是逻辑值, flush 时编码 ✓;
- 标量投影 `select po.status`: 全项目 **0 处**(实测), 无此雷;
- service 层无 createSQLQuery(decoration 实测), SQL 字符串全部集中在 DAO 层, 改写面可控。

**Interceptor 触及不到、必须手工改写的面**(审计定量):

| 类别 | 全项目数量 | 改写模式 |
|---|---|---|
| getCriterion 条件(含 DaoImpl:59 重复实现) | 102 处(status 62 + type 40) | **注册表自动改写**, 见 §6(a) |
| 直接 `Restrictions.*("status"/"type")` | 286 处 | `ObfRestrictions` 工具类手工替换 |
| 原生 SQL/HQL 字符串里过滤 status | 108 行 | 参数改传 `Codec.tag(v)`, 列名改 `status_tag` |
| 批量 DML `update...set status` | 37 行/~20 文件 | 改"查 id+salt → 逐行 setStatus"循环 |
| `insert into...select` | 15 处 | select 列表**必须带上 obfSalt/statusTag** |
| GROUP BY status | 8 行(report 模块) | group by status_tag + `untag` 回译展示 |

## 6. 查询路径改写规范

**(a) getCriterion 收口(自动)**: `TopQuery.getCriterion`(`GenericDaoImpl:200-237`)与 `DaoImpl` 内重复实现(`:59-89`)两处加注册表判断——属性在 ObfRegistry 中且 op ∈ {eq, ne, in} 时: 自动换属性名为 tag 属性、参数经 τ 折算, 调用方零改动。查询条件三层体系(QUERY_CONDITION_GUIDE)走的就是这条路, 装修单列表"状态"下拉条件自动生效。

**(b) Restrictions 直调(手工)**: 新增 `ObfRestrictions`(`eq/in/notIn` 三个静态方法, 内部做属性名+参数折算), 按字段清单逐处替换。

**(c) 原生 SQL(手工)**: `and status = :status` → `and status_tag = :status`, 参数绑定处 `codec.tag(v, ns)`。如 `DecorationDaoImpl:522` 的 `d.status NOT IN (4,6)` → `d.status_tag NOT IN (:tags)`(NOT IN 在双射下语义保持 ✓)。

**(d) 批量 DML(手工)**: `update ... set status=:target where status=:source`(`DecorationBelongDaoImpl:76`)→ 先 `select id, obfSalt` 圈定行, 再逐行 `po.setStatus(target)+update`(写路径走 interceptor 自动编码)。此类通常是业务编排循环, 量级可接受。

**(e) GROUP BY(手工, 仅 report)**: `GROUP BY status` → `GROUP BY status_tag`, 展示前 `untag` 回译。对账恒等式见 §8。

**(f) 语义闸门**: op 为 `lt/gt/between` 的 status 条件在双射下**语义破坏**(tag 保序但序无语义), 逐字段清单里作为**准入检查项**: 存在此类用法 → 要么改写为枚举 in, 要么该字段暂缓纳入。

**(g) 位掩码**: `otherStatus`(op=`and` 位与)不纳入, 常驻明文。

## 8. 迁移与上线

**分阶段**:
- 阶段 0(基建): ObfCodec + ObfEntityInterceptor + ObfRegistry + ObfRestrictions + 迁移 job 框架 + `scripts/obf_codec.py`(Python 参考实现) + q.py/修数纪律文档; dev 全绿后进 test;
- 阶段 1(试点): 仅 `decoration.decoration.status` 一表两列;
- 阶段 2(推广): A 档字段逐个按 checklist 上, 每字段独立可回滚。

**单字段上线九步**(以试点为例):

1. **准入检查**: 域类型 tinyint(1) ✓、无 lt/gt/between 用法 ✓、PO 唯一映射该表 ✓;
2. **DDL 先行**(先于 jar, 旧 jar 不受影响): `ALTER TABLE decoration.decoration ADD COLUMN obfSalt SMALLINT NOT NULL DEFAULT 0, ADD COLUMN statusTag TINYINT(1) NULL, ADD INDEX idx_statusTag(statusTag);` — 5.6 在线 DDL, 73 万行分钟级, 低峰执行;
3. **备份**: `tempbase.bak_<单号>_decoration` 常规三件套(备份先行, 回报行数);
4. **低峰停写窗口**(tomcat 双实例全停, 预计 5~15 分钟);
5. **迁移 job**(Java, 独立 main): JDBC 按 doid 分段拉 `(doid, status)` → 生成盐+enc+tag → 批量 UPDATE(batch 1000), 73 万行 ≈ 分钟级; 可断点续跑(盐=0 的才处理, **幂等**: 盐>0 视为已迁移, 天然支持重跑);
6. **换 jar 重启**(新增 interceptor + 查询改写代码);
7. **对账恒等式**: 迁移前 `GROUP BY status` 各值计数 == 迁移后 `GROUP BY statusTag` 各值计数(双射保证), 一条 SQL 完成终验;
8. **业务抽样**: 页面开装修单详情/列表按状态过滤/推进状态一次;
9. **放开**。

**回滚**: 窗口内 = 停服 → 备份表回插 status/清盐清 tag → 旧 jar 起服(原状态完全复原); 窗口后 = 新产生的行走 job 反向重编码回明文(机制同款, 提供反向模式)。

**零停机备选**(不推荐首选, 仅备案): 依赖"盐=0 明文直通"规则 + 过渡期双格式查询(`(obfSalt=0 AND status=v) OR (obfSalt>0 AND statusTag=τ(v))`, getCriterion 收口点可自动拼)——免停写窗口但过渡期查询条件翻倍复杂度, 且过渡期内批量 DML/对账都更绕。**推荐**仍走短停写窗口, 简单可证。

**常驻安全网**:
- `salt==0 → 明文直通`规则**常驻**代码(旁路写入一条明文行不至于读炸, 且迁移 job 幂等依赖它);
- 巡检(可并入现有 job): 扫 `盐>0 且 dec(status) ∉ 该字段合法值域` 的行 → 告警, 兜住未来遗漏的旁路 UPDATE(它写的是逻辑值, 解码出来大概率越域, 能被发现)。

## 11. 备选方案对比 (为什么不做)

| 方案 | 做法 | 否掉理由 |
|---|---|---|
| B. 全局固定双射(单列) | 存储值=τ(logical), 全表同状态同值, 无盐无 tag 列, 查询=常量折叠 | **不满足"每单不同"这一需求核心**; 已知一单明文即逐值破译全库; 仅供对比量级: 实施成本约为本方案的 60% |
| C. 无 tag 列, 查询后内存过滤 | 主列逐行乱序, WHERE status 全部改成 Java 后过滤 | 分页 count/大表过滤全部失效(decoration 列表页即重灾区); 仅对查询点≈0 的个别字段作为局部选项 |
| D. 只在导出/接口层混淆, 库里存明文 | 不动存储 | 不满足"保存数据库即混淆"的需求本体 |
| E. UserType/CompositeUserType | 类型层编码 | `nullSafeGet/Set` 拿不到行内盐/主键, 逐行键控不可行; 查询改写同样逃不掉 |

## 附录: 效果示意

同一逻辑状态 `3(签约)`, 两张不同装修单:

```
单A  orderId=2501110001  obfSalt=45231  →  status=102   statusTag=87
单B  orderId=2502110002  obfSalt=51799  →  status=77    statusTag=87
```

- 只看库: 两行 status 列一个 102 一个 77, 看不出同状态也看不出语义;
- 两行 statusTag 相同 → 观察者仅能得知"这两单状态一样", 不知道是签约还是废单;
- 应用内: `decoration.getStatus() == DecorationPO.STATUS_SIGNED_INT` 照常成立;
- 列表页选"签约"过滤 → `WHERE status_tag = 87` 命中两行, 分页计数不变。

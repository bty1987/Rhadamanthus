## 三、唯一要新建的后端逻辑（3 件）

### 3.1 自动发券引擎（decoration 模块，事件驱动，用户拍板 2026-10-30：无 Job）

**触发机制 = 收款/提现链插桩**（用户拍板，推翻 Job 方案；🔴预付款退款走**提现接口**非 returnPayment）：每次主材预存收/提现时同步判断发券，实时到账：

| 插桩点（payment 模块，先例充分：4 处 DaoImpl 已 import decoration） | 触发条件 | 引擎动作 |
|------|---------|---------|
| `PaymentServiceImpl.collectPayment`（收款入账） | `paymentType=2`(主材) + 订单公司有 type=20 活动 | 现算应得数 → diff 补发券 |
| `PaymentServiceImpl.withdrawPayment`（预付款提现 = 退款，368行；内部 `setType(TYPE_EXTRACT)`+save 即流水落库点，直提/审批链共用此入口） | 同上 | 现算应得数 → 多余**未参与抽奖**的券置失效（已抽奖(11)/已领(10)不回收） |

> 落码时验证审批通过后的提现执行路径是否同样收敛于 withdrawPayment（双闸=直提+审批链，流水写入点在此方法内）；若审批链另有落库出口则补插一处。

- 插桩点收尾已有 messagecueuing 事件先例，风格照抄；发券为纯库操作同事务完成，无事务内外部调用风险（customernotice 教训不适用）
- **活动定位锚点（2026-11-01 拍板 type=20 复用）**：引擎找活动条件 = `company + type=20(抽奖券) + 窗口内 + status=有效`——同公司同窗口的其他类型活动（如元旦预存礼）不会被误触发发券；规则行定位 = 该活动 `aid` 下 `activityrule` 各启用行（ruleType 指标规则）
- **唯一性闸（应用层，count 化）**：`addActivity` / `updateActivityForStatus` 经 `countActivityForLottery`(SQL count) 判 同公司 + type=20 + 时间窗重叠 + 启用状态 冲突即报 160063（MySQL 5.6 无部分唯一索引，只能应用层管）——防运营配错两个活动叠加发双倍券
- **活动配置驱动参与范围**（无公司清单）：配了活动才发，没配跳过——配活动=参战，不配=不参战
- **预存口径定案（用户拍板）**：**净额 = 活动期内收款累计 − 提现（退款）累计**（withdrawPayment 的 TYPE_EXTRACT 流水即扣减项）
- awardstock 不加"券类型"（2026-10-30 讨论定案）：不同活动的券由 `activityrule.asid` 绑定关系天然隔离，无需档案自身带类型；奖品管理页筛选便利为可选增强，暂不做

**发券公式（Σ 框架，2026-10-30 规则表定案）**：

```
应得券数(orderId) = Σ(该活动各启用规则行的应得)
  ruleType=1 签约赠   : 窗口内签约 ? tickets : 0                          ← 本次"签约得1张"
  ruleType=2 预存每满 : min(floor(净额 ÷ perAmount) × tickets, maxTickets) ← 本次"每满3万送1张"用此行
  ruleType=3 预存阶梯 : Σ(净额 ≥ threshold 的 tickets)，同类型多行           ← 未来非线性阶梯
```

**上线补发**（用户拍板 11-05 上线须补发）：全量补发入口（临时 Action，跑一遍窗口内签约单 diff 补发），上线当天手动触发一次，补齐 11-01 起存量；跑完保留不删（防万一重跑幂等）。

**手动兜底**：`addDecorationActivityItem` 照旧可用（客服补单）。

### 3.2 抽奖系统对接（用户拍板 2026-10-30：零同步、零接口，直读直写库）

抽奖系统**直连数据库**获取奖池、回写中奖结果，ERP 侧不开发任何导出/导入/回调接口：

- **奖池读取**（抽奖系统侧 SQL，ERP 只提供口径）：`decoration.decorationactivityitem` 有效券行 = `no LIKE 'LT%'`（自动引擎发的券编码前缀）+ 活动窗口内；展示字段 JOIN `communion.company.name`(城市分公司) + `communion.customer.name`(客户姓名) + 本表 `no`(券编码)/`orderId`(订单号)
- **中奖回写**（开奖后直接 UPDATE，2026-11-01 拍板）：`state` 置 **11(抽奖，参与抽奖)**；是否真中奖/中什么奖（奖项名）后续对接抽奖系统由其说明；ERP 侧无加列（state 既有字段新常量 STATUS_DRAW_INT）
- 中奖轨迹表不强制（抽奖系统直写库带不了轨迹，可接受）；核销走现成 state=10，礼品部照旧
- 权限：抽奖系统已有直连生产库的成功先例，授权路径已打通，无需额外协调（用户拍板 2026-10-30）

### 3.3 前端小改（一处）

- **Applet activityItem 页**：wxml 显示 `no`（券编码，可挂现成 barcode.js 出条码）+ 按 `state=11(抽奖)` 渲染中奖提示（奖项名后续对接抽奖系统取）
- **ERP WebContent：零改动**（活动管理/装修单活动区块/查询页全现成）

# 预付款提现 · 主材可用积分校验方案

> 版本: v1.1（口径已拍板,已落码）
> 日期: 2026-10-26
> 状态: 已实施——口径=cppoint.spoint 主材积分余额(MemberAction.makeMemberOrder 兑换链路会更新该字段,801行 setMaterialPoint(sub(totals, amountMaterial)));dpoint=装修积分(商城主扣)
> 需求: 预付款提现时,验证主材可用积分是否符合要求

## v1.1 定案

- **Q1 口径**：拍板为 **cppoint.spoint**（主材积分余额）——MemberAction.makeMemberOrder 积分兑换链路同时扣减 dpoint/spoint,spoint 即主材积分可用余额;生产 970 户中 spoint 全 ≤0（通道历史未产生正积分）,校验上线零存量影响;
- **Q2 规则**：资格闸——spoint > 0 时拦截提现主材预付款（新码 150101）,spoint ≤ 0（含负值脏数据,Q5 一并定案）放行;
- **Q4 时点**：双闸——submit 提交资格审 + approve 通过复核;
- **实现形态**：硬校验（无配置开关,无 SQL——生产 spoint 全≤0 上线零影响）。

## 一、现状梳理（代码 + 生产实测）

### 1.1 预付款提现链路（approval 模块，已存在）

`ApprovalPaymentWithdrawServiceImpl` 三方法：

| 方法 | 时点 | 现有校验/动作 |
|------|------|--------------|
| `submitApprovalForPaymentWithdraw` | 提交审批 | 同单审批中防重(240004) → 装修单存在(140013) → 预付款行存在+余额充足(150010，不预扣) |
| `approveForPaymentWithdraw` | 审批通过 | 复核余额(150010) → **真扣** advancepayment 对应 paymentType 余额 → AdvanceReceipt 收据 → Payment 提现流水(EXTRACT) → 主材提现刷销售比例 → 通知 |
| `refuseForPaymentWithdraw` | 驳回 | 仅查子记录 |

提现类型 `paymentType`：0=合同预付款 / 1=工程预付款 / **2=主材预付款** / 3=正林预付款。本需求只针对 **paymentType=2（主材预付款）**。

### 1.2 积分体系（customer 模块，已存在）

- 账户表 `customer.cppoint`，**按 (company, cid, orderId) 装修单维度**建账（`queryPointAccountByOrderId`）；
- 三类积分列：`dpoint` 装修积分 / **`spoint` 主材积分** / `opoint` 运营积分，另有 `point` 总额列；
- 加减通道：`PointAccountService.updatePoint` / `consumePoint`——**仅前端 HTTP 端点触发（updatePointAccountForOperatePoint / consumePoint.do），后端销售/退货业务链无自动挂接**；
- `consumePoint` 对 dpoint/spoint 自带"积分不足"闸（330049）与全快照流水（PointRecord TYPE_ADDUP/USERUP）；
- 积分商城兑换（MemberServiceImpl）扣的是 **dpoint 装修积分**，不走 consumePoint。

### 1.3 生产数据事实（2026-10-26 只读库实测）

| 事实 | 数值 | 含义 |
|------|------|------|
| cppoint 账户总数 | 970 | 按单建账覆盖面尚可 |
| **spoint > 0 的账户** | **0** | 🔴 **主材积分通道生产上从未产生过正积分（休眠中）** |
| spoint = 0 / < 0 | 969 / 1 | 1 个负值为历史脏数据 |
| dpoint > 0 | 69 | 装修积分通道在用（商城兑换侧） |
| 提现链路与积分体系交集 | **零** | 两套体系现状互不感知 |

## 二、需求解读与 🔴 待拍板开放问题

需求原文"预付款提现时验证主材可用积分是否符合要求"存在口径歧义，以下 5 项需拍板后落码：

**Q1 积分口径**（最关键）："主材可用积分"指什么？
- (a) `cppoint.spoint` 主材积分 —— 字面吻合，但生产当前全 ≤0（通道休眠），校验落地即空转，属**为积分新政策提前铺路**；
- (b) `cppoint.dpoint` 装修积分 —— 商城在用的通道；
- (c) `point` 总积分。
- 推荐 (a) 字面口径；若业务实际意图是 (b)/(c)，框架不变仅换字段。

**Q2 校验规则**（"符合要求"的定义）：
- **R1 资格闸**：spoint ≤ 0（或 = 0）才允许提现主材预付款；不符抛错拒绝。语义=积分未结清不许提走预付款；
- **R2 联动扣回**：按提现额折算应扣积分（比例参数化，如每千元预付款扣 N 积分），spoint 足够则**提现通过时自动扣回**，不足拒绝。语义=提现即核销对应积分权益；
- **R3 仅提示**：不阻断，提交页展示积分余额供经办人判断。
- 推荐 R1（资格闸）——规则清晰、不引入折算比例歧义；R2 需先定积分政策。

**Q3 折算比例**（仅 R2 需要）：主材预付款与积分的换算系数，建议 systemconfig 配置化而非硬编码。

**Q4 校验时点**：仅提交闸（submit）/ 仅通过闸（approve）/ **双闸**（submit 资格校验 + approve 复核+扣回，防提交→通过期间积分变动）。推荐双闸。

**Q5 负值账户**：生产存在 1 个 spoint<0 脏账户。负值视为"不符"（拦截并顺手修数）还是视为"符合"（≤0 即通过）？推荐按 R1 的 ≤0 口径自然通过，脏数据另行修数。

## 三、推荐方案（框架先行，规则参数化）

采用 **Q4 双闸 + Q2/R1 资格闸** 为默认实现（规则与阈值 systemconfig 配置驱动，未配置=功能休眠 fail-open，零风险上线）：

### 3.1 校验逻辑（伪码）

```
若 paymentType != 主材预付款(2)  -> 跳过（其余三类提现不受影响）
查配置 withdraw.point.check（缺省未配置 -> 功能休眠，直接放行）
查积分账户 queryPointAccountByOrderId(company, cid, orderId)
  账户不存在 -> 无积分记录 -> 放行
  spoint > 配置阈值(缺省0)  -> 抛 150101「主材可用积分不符，不可提现」(submit) / 同样拦截(approve)
```

### 3.2 改动清单

| 层 | 文件 | 改动 |
|----|------|------|
| Service | `approval/ApprovalPaymentWithdrawServiceImpl` | ① submit 第 4 步后插资格校验；② approve 第 3 步余额复核后插复核校验；注入 customer 模块 `PointAccountService`（跨模块依赖先例已有：本类已注入 customer.DecorationService） |
| Service | `customer/PointAccountService` | 零改动（复用 queryPointAccountByOrderId 只读查询；若采 R2 再复用 consumePoint 自带闸与流水） |
| 错误码 | `docs/03-API文档/API/error.md` | 新码 **150101 主材可用积分不符，不可提现**（150 段款项域，150100 已被占用顺延） |
| 配置 | communion.systemconfig | 键 `withdraw.point.threshold`（spoint 允许上限，缺省 0）+ 键 `withdraw.point.check`（开关，可选——键不存在即休眠，无需开关键） |
| SQL | sqls/communion/ | systemconfig 插键 1 行（DML，先于/后于 jar 均可——键不存在时功能休眠） |
| 前端 | 提现提交弹窗 | 零强制改动（150101 自动弹出提示）；可选：提交前查积分账户展示"当前主材可用积分" |
| DDL | 无 | 复用 cppoint 现有结构 |

### 3.3 若拍板为 R2（联动扣回）的增量

approve 通过扣回走 `consumePoint`（spoint 腿自带 330049 不足闸 + PointRecord 流水快照），提现事务与扣积分同事务回滚；另需 PointRecord 备注关联提现审批 aid 便于对账（PointRecordPO.init 无 comment 位，需评估加列或用 orderId 位复用——倾向加 comment 列，DDL 一列）。

## 四、部署与风险

- 部署物：approval jar（1 个）+ systemconfig 键 1 行；无 DDL、无前端强制发版。
- 上线序：任意（键未配置时新 jar 行为与现状完全一致——fail-open 设计保证零风险先上 jar，业务想启用时插键即生效，改库免重启）。
- 风险点：
  1. 口径若非 spoint（Q1 选 b/c），框架不动仅换字段与文案，返工成本约一行；
  2. 积分加减纯前端触发意味着积分数据可信度依赖操作纪律——校验闸只能挡"账户数字不符"，挡不住绕过端点的手工改数（如需硬管控需先给积分加减加后端业务挂接，另行立项）；
  3. 审批中存量单不受影响（approve 复核闸对存量单同样生效——若存量单积分不符会被拦，上线前需核对审批中主材提现单，当前生产此类单极少）。

## 五、测试要点（拍板后补充用例）

1. spoint=0 提现主材预付款 → 通过（配置启用后）；
2. spoint>0 提现主材预付款 → submit 150101 / approve 150101 双闸各拦一次；
3. spoint>0 提现合同/工程/正林预付款 → 不受影响；
4. 无 cppoint 账户的单提现 → 通过；
5. 配置键删除 → 功能休眠全放行；
6. 提交时 spoint=0 通过、通过时 spoint>0（并发窗口）→ approve 闸拦截。

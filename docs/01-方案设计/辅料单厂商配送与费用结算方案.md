## 1. 背景与需求

**需求原话（2026-10-26 用户定调）**：辅料单模仿外辅单，增加**配送**和**分配厂商**功能，同时可以**计算费用信息**，增加**费用额**和**结算额**。

**四项拍板**：

| # | 决策点 | 拍板 | 含义 |
|---|--------|------|------|
| 1 | 状态机 | **独立** | 不照搬外辅 0-5 状态，辅料用自己的扩态设计（见 §3.1） |
| 2 | 费用口径 | **自动算**，后续可支持手工维护 | 首期按 data.aoodscharge 模板自动计算，不建明细表；手工维护留扩展位（见 §5.2） |
| 3 | 结算额 | **单列** | 不做外辅 rbalance 实结算/vbalance 虚结算双列，只加一个结算额列 |
| 4 | 厂商端入口 | **PC** | 本期只做 PC 管理端（含厂商登录视角），不动微信小程序 |

## 2. 参照模型盘点（外辅单 → 辅料单差距）

外辅单（`OccessoriesPO` + `OccessoriesAction` 17 接口）是现成蓝本，逐项对照：

| 能力 | 外辅实现 | 辅料现状 | 本方案动作 |
|------|---------|---------|-----------|
| 分配厂商 | `supplier`(UserPO) + `bindOccessories`（置厂商→状态推已绑定→监理收"已分配完厂商"消息）+ `pageOccessoriesForSupplier` 厂商视角分页 | 无 supplier 字段 | 加列 + `bindAccessories` + `pageAccessoriesForSupplier` |
| 配送 | `deliver/deliveTime/receiver/receiveTime` + delive/receive 接口，状态 2已配送→3已接收 | **已有** `deliver/deliverTime/fetchTime` 与 `deliveAccessories`（出货2→到货6） | 零改动，沿用现有出货→到货链 |
| 费用计算 | `charge` 总额 + `rcharge` 结算费用 + OccessoriesCharge 明细表 + `batchOccessoriesCharge`；公式 `charge = ∑((price+surplus)×num)`（`sqls/inventory/10` 注释先例） | 无任何费用字段 | 加 `charge` 列 + 模板自动算（无明细表，见 §5.2） |
| 结算 | `balancer/balanceTime` + `rbalance`/`vbalance` 双列 + `balanceOccessories`（置状态）/`updateOccessoriesForBalance`（改金额）双接口 | 无 | 加 `balance` 单列 + `balanceAccessories` 合一接口 |
| 状态机 | 0初始→1已绑定→2已配送→3已接收→4已结算→5已完成 | 0初始/1预出/2出货/3撤销/4拒绝/5退回/6到货/7审批 | **独立**：现有 8 态全保留，仅新增 8=已结算（§3.1） |

**关键现状事实**（2026-10-26 核对）：
- 辅料配送链已存在：`deliveAccessories` 校验状态=出货(2) → 置到货(6)+deliver+deliverTime，**本期配送零开发**
- 外辅 bind 语义：状态∈{初始,已绑定} 可绑/改派，`setSupplier(userDao.get(uid))` + 监理消息
- 外辅结算语义：状态=已接收才可结算，`balanceOccessories` 只置状态/人/时间；金额走另一接口
- 费用模板取数唯一入口：`AoodsChargeDao.queryAoodsChargeByAid(aid, type)`（status=启用、sort 升序）
- 前端厂商选人：`com.initTypeahead('supplier', api.personel.querySupplierByPinyin, "supplier.pinYin", ..., "suppliers", "uid", "userName", null)`（occessories.js:110 同款）
- 外辅前端单文件双视角：`pageType == "supplier"` 切厂商固定视角（occessories.js:57），辅料可照搬

## 3. 总体设计

### 3.1 状态机（独立设计）

现有 8 态**全部保留不动**（0初始/1预出/2出货/3撤销/4拒绝/5退回/6到货/7审批，在跑生产语义零风险），仅新增一个终态：

```
0初始 → 1预出 → 2出货 → 6到货 → 8已结算(新增)
   ↘ 3撤销    ↘ 4拒绝/5退回        (7审批旁路不变)
```

- **新增 `STATUS_BALANCED_INT = 8`（已结算）**：唯一入路 = 到货(6) 态调 `balanceAccessories`；终态，cancel/refuse/明细增删改一律拦截（复用 260024）
- **分配厂商不占状态位**（与外辅的本质差异，"独立"的核心取舍）：外辅把绑定当状态（1已绑定），辅料若加"已分配"态会与在跑的预出/出货链交叉污染。辅料将 supplier 作为**属性行为**——状态∈{0初始,1预出,2出货} 可分配/改派（覆盖式），只落字段+发消息，状态不动
- 状态字典同步：communion.constant 插 `key=8 '已结算'`（驱动列表翻译+前端逻辑值）

### 3.2 费用自动算（不建明细表）

**公式（对齐外辅先例）**：
```
charge(费用额,厘) = Σ_明细( num × Σ_启用费用行(price + surplus) )
```
- 费用行来源：`accessoriesItem.gid + 单.company → data.aoods(gid, company) → aid → queryAoodsChargeByAid(aid, null)`（与外辅创建页 occcessories2create.js 模板预填同源）
- **首期无 AccessoriesCharge 明细表**：费用额是派生值，随明细增删改实时重算，不落明细不过度设计
- **手工维护扩展位**（拍板②的"后续"）：charge 为普通列，后续需要时再加明细表（照 OccessoriesCharge）或覆写开关接口，本期不建
- **surplus 浮动额计入已定稿**（2026-10-26 拍板①）：照外辅公式 `(price+surplus)×num` 全额计入，超阶(type=1)费用行同样照算不区分

### 3.3 结算（单列合一接口）

- `balance` 单列（结算额，厘），不做实/虚双列
- `balanceAccessories` **合一接口**（外辅是 balance+updateForBalance 双接口）：入参 balance 金额，校验状态=到货(6)，一次写 balance + balancer + balanceTime + status→8
- 首期单条结算；批量 `batchBalanceAccessories` 列遗留（外辅有 batchBalance 先例，抄即可）

### 5.2 费用计算实现要点

```java
// AccessoriesServiceImpl.recalculateCharge(aid) 草案
private long recalculateCharge(int company, List<AccessoriesItemPO> items) {
    long charge = 0;
    for (AccessoriesItemPO item : items) {
        AoodsPO aoods = aoodsDao.queryAoodsByGid(item.getGid(), company);  // gid+company 唯一
        if (aoods == null) continue;                       // 无模板按0，不阻断
        for (AoodsChargePO c : aoodsChargeDao.queryAoodsChargeByAid(aoods.getAid(), null)) {
            charge = Arith.add(charge, Arith.mul(item.getNum(), Arith.add(c.getPrice(), c.getSurplus())));
        }
    }
    return charge;  // 厘
}
```

- `AoodsDao` 需补 `queryAoodsByGid(gid, company)`（如已有同义查询则复用）；🔴 若同公司同 gid 存在多行 aoods，聚合全部费用行并**告警日志**（数据异常不应静默取一）
- charge 不参与 `accessoryLimit/accessoryTotal` 上限口径（那是 total 口径，两个量纲不混算）

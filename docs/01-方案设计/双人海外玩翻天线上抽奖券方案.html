双人海外玩翻天 · 线上抽奖券技术方案02

壹需求理解 · 三块

NO.1发券
① 窗口期签约即得 1 张（方林 / 爱林 / 恩林 / 屿林 / 1918 五板块）； ② 预存主材款阶梯再送：方林 3万/张、恩林 2万/张、屿林 3万/张、爱林 2万/张、别墅1918 6万/张； ③ 仅窗口期新签约参与，老单档期内预存不算； ④ 二次补缴按累计预存补发，要求"尽快显示"。
NO.2券
每张唯一编码；编码关联订单；中奖展示 订单号 + 城市分公司 + 客户姓名；客户端可见编码。
NO.3抽奖
中奖公示（编码 / 订单号 / 城市分公司 / 姓名）；同一客户限中一次；中奖客户端提示"恭喜您获得xxxx奖项，请与礼品部联系核销"；全国门店员工查询入口。

用户架构现有承载（零新建表）现状

叁要新建的后端逻辑

3.1自动发券引擎 —— decoration 模块 · 事件驱动 · 无 Job

拍板触发机制 = 收款 / 提现链插桩，每次主材预存收 / 提现时同步判断发券，实时到账；预付款退款走提现接口 withdrawPayment，非 returnPayment。
插桩点（payment 模块）触发条件引擎动作
PaymentServiceImpl.collectPayment
收款入账		 paymentType=2(主材) + 订单公司有活动配置 现算应得数 → diff 补发券
PaymentServiceImpl.withdrawPayment
预付款提现 = 退款（368行；setType(TYPE_EXTRACT)+save 即流水落库点，直提 / 审批链共用此入口）		 同上 现算应得数 → 多余未中奖券置失效（abate，已中奖不回收）
落码时验证审批通过后的提现执行路径是否同样收敛于 withdrawPayment；若审批链另有落库出口则补插一处。插桩点收尾已有 messagecueuing 事件先例，风格照抄；发券为纯库操作同事务完成。
发 券 公 式 应得券数(orderId) = (窗口内签约 ? 1 : 0)
    + floor(活动期内收款净额 ÷ 模板money门槛)
净 额 口 径 · 已 定 案 净额 = 活动期内收款累计 − 提现（退款）累计
  • 活动配置驱动参与范围（无公司清单）：引擎判断订单公司是否在窗口内配了活动（activity by company），配了才发，没配跳过。
  • 上线补发（11-05 上线须补发）：全量补发临时 Action，跑一遍窗口内签约单 diff 补发，上线当天手动触发一次，补齐 11-01 起存量；幂等可重跑。
  • 手动兜底：addDecorationActivityItem 照旧可用（客服补单）。

3.2抽奖系统对接 —— 零同步 · 零接口 · 直读直写库

  • 奖池读取（抽奖系统侧 SQL，ERP 只提供口径）：decorationactivityitem 有效券行 = no LIKE 'LT%' + 活动窗口内；JOIN communion.company.name(城市分公司) + communion.customer.name(客户姓名) + 本表 no(券编码) / orderId(订单号)。
  • 中奖回写（开奖后直接 UPDATE）：awardName 列写奖项名、state 置 1；ERP 侧唯一工作 = 加列 DDL（ALTER 只加列，幂等）。
  • 中奖轨迹不强制（直写库带不了轨迹，可接受）；核销走现成 state=10，礼品部照旧。
  • 权限：抽奖系统已有直连生产库成功先例，无需协调。

3.3前端小改 · 一处

  • Applet activityItem 页：wxml 显示券编码 no（可挂现成 barcode.js 出条码）+ 按 awardName 渲染"恭喜您获得{awardName}，请与礼品部联系核销"。
  • ERP WebContent：零改动（活动管理 / 装修单活动区块 / 查询页全现成）。

# 数据-工程节点 集团版/分子公司关联 调整方案

> 编制日期:2026-10-06 / **v3 修订:按拍板定稿**——无快照、全字段自由、纯关联归集、不做批量同步;创建必选集团节点由**前端承载、后端零校验**;seiya 通道不动(company 空落 0 为既定行为);存量归纳一次挂接
> 范围:`data.constructionnode` 表、ConstructionNodeAction/Service/DAO/PO/VO(`src/com/fanglin/data/`)、`WebContent/views/data/constructionNode.html` + `js/data/constructionNode.js`(老版)、`app/js/data/constructionNode.js`(app 版)
> 状态:**方案稿,待确认后实施**
> 模型对齐:noods 定材「集团主数据/分公司引用行」先例(`docs/10-指南手册/NOODS_GROUP_COMPANY_ADJUSTMENT.md`,pnid 挂接 752 行已生产执行);**本方案是它的极简版:只关联,不快照,不同步,后端零校验**

## 1. 现状

### 1.1 数据模型

`data.constructionnode` 逐公司全量独立配置,`company` 列隔离,~100 公司各维护一套节点集。查询链路全部 `eq(company, queryCompany())`:

- `pageConstructionNode` / `queryConstructionNode`(ConstructionNodeDaoImpl.java:28,40)——老版数据页、app 版节点页、seiya 平台开工预排(A20251208ServiceImpl.java:981)、客源施工页(ConstructionServiceImpl.java:67)
- `countConstructionNode(process, company)`(:49)——完工进度推进判断(ConstructionScheduleServiceImpl.java:397、A20251208ServiceImpl.java:727)

现状操作面:老版页面**创建按钮被注释**(constructionNode.js:78-83),仅剩编辑;app 版有完整增改。新公司/新节点的实际维护方式是逐公司 SQL(新公司播种=从别公司整套复制,见 sqls/misc/北京分公司数据创建SQL.sql:77 `SELECT ... WHERE company = 66` → 91/92/93)。

### 1.2 消费方(必须零影响)

全部按 `cnid` 主键直读,共 14 处:`NormtimeItemServiceImpl:66`、`NormriceItemServiceImpl:122`(定额)、`AddReduceServiceImpl:274`、`DecorationAdditionServiceImpl:106`(增减项)、`PaymentServiceImpl:317`(款项)、`ConstructionScheduleServiceImpl:322,397,604`(施工进度/环节)、`DrawLineServiceImpl:332,585,755`(放线)、`MaterialPlanServiceImpl:512`(材料计划)、`A20251208ServiceImpl` 五处(seiya 平台)。

两个硬引用形态决定了方案边界:

1. **`decoration.projectStatus` 存的就是 cnid**——装修单直接挂自家公司节点行,cnid 一旦变更即需全量修数;
2. **`constructionschedule` 等七表按 `cid+cnid` 活引用**。

### 1.3 痛点

1. 节点集无集团归集关系,~100 公司各一套同名节点,漂移无对账手段;
2. 新开公司/新增节点逐公司发 SQL(挪 sort + 七表引用同步,单次 120+ 行);
3. seiya 平台通道 `syncConstructionNodeForPlatforPm`(A20251208ServiceImpl.java:1158)按 cnid 直加/改,与集团/分公司语义无关。

### 1.4 身份机制现成

`queryCompany()` 集团账号=0、分公司=本公司 id(BaseAction.java:109),`company` 过滤天然隔离;`addConstructionNode` 已有 `company null→0` 兜底(ConstructionNodeServiceImpl.java:132)。

## 2. 方案(v3 拍板版)

**加一列 `pcnid`,只做关联归集,不动任何字段语义:**

| company | pcnid | 语义 |
|---|---|---|
| 0 | 0 | 集团行(集团工程节点主数据) |
| >0 | 0 | 自治行(存量现状,未关联) |
| >0 | >0 | 关联行(全字段自由,pcnid 仅记录归属哪个集团节点) |

- **无快照**:关联行与集团行之间没有字段复制/锁定/同步关系,所有字段照常本地编辑;
- **不同步**:集团行后续怎么改都不波及关联行(「一次维护好」);
- **关联的用途**:节点归集对账(同名节点散落各公司 → 一眼看出谁挂谁)、按集团节点维度的统计与后续治理抓手;
- **创建规则(前端承载)**:分公司账号创建工程节点,页面强制先选一个集团节点(集团没有的先在集团下维护);**后端不做任何校验**——对齐 noods 先例「前端控权」原版,内部 ERP 可接受;
- 列名 `pcnid` 对齐 noods `pnid` 命名(parent cnid)。

## 3. 详细设计

### 3.1 数据库(DDL)

```sql
-- 幂等写法按 NOODS_ADD_PNID.sql 同款 information_schema 判断,此处示意
ALTER TABLE data.constructionnode
  ADD COLUMN pcnid INT(11) NOT NULL DEFAULT 0 COMMENT '集团节点cnid:0=集团行/未关联,>0=关联的集团行cnid(全字段自由,仅归集关系)' AFTER cnid,
  ADD INDEX idx_pcnid (pcnid);
```

存量全部 pcnid=0(未关联),行为与现状完全一致,**零迁移零风险窗口**。

### 3.2 后端改动清单(最小化)

| # | 文件 | 改动 |
|---|---|---|
| 1 | DDL | pcnid 列 + 索引(sqls/data/CONSTRUCTIONNODE_ADD_PCNID.sql) |
| 2 | ConstructionNodePO / VO | 各加 `pcnid` 字段(Long);查询链路 ptv 走 copyProperties 自动带出,零改动 |
| 3 | ConstructionNodeServiceImpl `addConstructionNode` | 仅一行 `setPcnid(VO 值,null 兜底 0)`——**无校验、无错误码**;updateConstructionNode **零改动**(pcnid 不可换绑:关联关系建行即定,解绑/换绑走运维 SQL) |

### 3.3 前端(两版,规则由前端承载)

## 4. 存量归纳与挂接(一次性,独立可后置)

三步 SQL,一次维护好,不做常驻同步:

**① 盘点归纳(出合集清单,业务确认)**

```sql
-- 节点名合集 + 覆盖公司数(集团合集的候选底稿)
SELECT name, COUNT(DISTINCT company) AS companyCnt, MIN(cnid) AS sampleCnid
FROM data.constructionnode WHERE company > 0
GROUP BY name ORDER BY companyCnt DESC, name;
-- 核验:同公司内 name 是否唯一(挂接键唯一性前提)
SELECT company, name, COUNT(*) FROM data.constructionnode WHERE company > 0 GROUP BY company, name HAVING COUNT(*) > 1;
```

**② 集团行播种**(业务确认合集后执行;代表行取覆盖面最大公司的现值,同新公司播种先例)

```sql
INSERT INTO data.constructionnode
  (name, precheck, postcheck, stacheck, fincheck, startalk, endtalk, sstid, estid,
   timeLimit, accessoryLimit, salaryLimit, salaryFloor, process, sort, proset, kino, kiname, mark, status, company)
SELECT name, precheck, postcheck, stacheck, fincheck, startalk, endtalk, sstid, estid,
       timeLimit, accessoryLimit, salaryLimit, salaryFloor, process, sort, proset, kino, kiname, mark, status, 0
FROM data.constructionnode WHERE company = 66 AND name IN (/* 合集清单,逐行列出 */);
```

- 直接 SQL 播种**绕过消息队列 NODE_CREATED 事件**——集团行非业务行,外部系统无需感知,可接受(备注留痕);
- sstid/estid 等模板引用在集团行里仅作参考值,不参与任何业务链路(消费方只读本公司行)。

**③ 挂接**(name 匹配,一条 UPDATE JOIN 全量挂,幂等)

```sql
UPDATE data.constructionnode c
JOIN data.constructionnode g ON g.company = 0 AND g.name = c.name
SET c.pcnid = g.cnid
WHERE c.company > 0 AND c.pcnid = 0;
```

- 前置:①的第二条核验通过(同公司 name 唯一)+ 集团行 name 唯一;
- **同名异写/一词多节点的例外行**:先查 `未挂接清单`(company>0 且 pcnid=0 的 name 不在集团合集),人工拍板逐行 UPDATE(NOODS_PNID_GROUP_MAPPING_UPDATE.sql 逐行映射先例);
- 集团行自身 pcnid 恒 0,不参与挂接;
- **不强制全量**:挂不上的保持自治(现状),不回填、不改名;
- 核验收口:`SELECT pcnid, COUNT(*) FROM data.constructionnode WHERE company>0 GROUP BY pcnid` 应≈每个集团行一组。

## 5. 上线序与回滚

🔴 **SQL(ALTER 加列)先于 jar**(PO 映射 pcnid 列,先 jar 后 SQL = Unknown column 即挂)。

```
① ALTER 加列(默认 0,执行后即等价现状) → ② jar fanglin-data-8.3.030 → ③ 老版+app 前端
④ 盘点归纳 → ⑤ 业务确认合集 → ⑥ 集团行播种 → ⑦ 挂接 SQL(④~⑦ 独立后置,一次执行)
```

- 回滚:全量 `UPDATE pcnid=0` 即回现状;列可保留无副作用;jar 回滚亦等价现状。

## 6. 风险与既定决策

1. **消费方零改动**(结构性保证):14 处 `get(cnid)` 主键直读、projectStatus、七表引用全部不动;pcnid 只进不出(查询链路 copyProperties 自动透出,仅新增展示用途);
2. **集团行误删/禁用无连带**:关联行不读集团行任何字段(无快照无同步),集团行只是归集锚点,禁用/删除不波及分公司业务;
3. **前端控权为既定设计**(拍板):绕过页面直调 addConstructionNode 可落未关联的分公司行、可重复关联——内部 ERP 按接受处理,后端零校验;治理靠挂接核验收口语句定期跑;
4. **seiya 平台通道保留意见**(拍板):平台下发报文 company 为空时经 `company null→0` 兜底落集团段(company=0),此行为不可控且**按为 0 既定接受**,不做核对、不加防护;若日后集团段出现脏行,运维 SQL 清理即可;
5. **name 匹配率**:挂接质量取决于各公司节点命名规范度;①的核验语句先行,例外行走人工映射(已拍板执行)。

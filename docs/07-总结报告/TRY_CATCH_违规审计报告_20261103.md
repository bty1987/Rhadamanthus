## 一、结论摘要

- 全系统共 **481 处 catch**,分布在 144 个文件。
- 按规则字面判定:**违规 131 处**(本报告全部列出);合规(FLException 包装/透传)103 处;豁免区 119 处;灰区(模块内嵌套 utils 工具类)128 处。
- 违规中**最大族群是"catch 后仅记日志继续跑"(52 处)**,其次是"catch 后 return 兜底"(26 处)与"空 catch"(27 处)。
- **违规高度集中**:esign(18)、log(13)、imports(11)、seiya(11)、swiftpass(11)、aliyun(8)、decoration(8)、dingding(7)八个模块占 85 处(65%)。
- 存在**两类结构性问题**需要规则层面裁决,不是逐条改码能解决的:
  1. **e签宝回调 Action `ESignAuthCallbackAction` 未在 Action 白名单内**(与 `DingTalkCallbackAction` 同类);
  2. **定时任务/日志基础设施的 Throwable 防中断兜底**(log 模块 13 处 + 各 Job)在规则中无豁免地位。
- 存在一批**带注释的刻意兜底**(elecsignauth 双写迁移、市场入库、拼音转换等),按规则字面属违规,应走"豁免评审"而非机械改造,已单列(第六节)。

## 二、规则基准与判定口径

### 2.1 规则原文要点(AGENTS.md)

1. `com.fanglin` 下所有业务代码(action/service/dao/po/vo)**禁止用 try-catch 做判断、流程控制、取值兜底**;
2. 豁免仅两类:**`core` 框架代码、`utils` 工具类**(对外部输入/IO 的解析防护属其本职);
3. 业务报错唯一出路:`throw new FLException(码, "消息"[, e])`(码值查 `docs/03-API文档/API/error.md`);
4. catch 的替代 = **前置校验**(判空 / `StringUtils.isNumeric` / 格式校验);
5. Action 层默认 `throws FLException` 禁本地 catch,豁免清单:`LoginAction`/`DoginAction`/`VerifyCodeAction`/`WMCodeAction`/`FactoryAction`/`LoginInfoAction`/`SecretAction`/`PhoneCallAction`/`PostarAction`/`SwiftpassAction`/`UploadAction`/`DingTalkCallbackAction`/`OssConfigAction`(共 13 类,本次已逐一核实均存在)。

### 2.2 判定口径

| 口径 | 定义 | 处数 |
|---|---|---|
| 违规 | 业务代码中 catch 体**未在所有路径上以 FLException 收尾**——吞掉、return 兜底、仅记日志、摸类型分支、抛非 FLException、Action 白名单外本地 catch | **131** |
| 合规 | catch 体内抛 `new FLException(...)` 或 `throw e`(FLException 透传,含反射 unwrap 后重抛) | 103 |
| 豁免 | 顶层 `core/`(35 处:拦截器/BaseAction/安全组件)、顶层 `utils/`(36 处:DateUtil/HttpUtil 等)、Action 白名单 13 类(48 处) | 119 |
| 灰区 | 模块内嵌套 `*/utils/`、`*/util/` 目录下的 HTTP/加解密/签名工具类(24 个文件)。按规则字面属违规,实质属工具类,单列不混入违规主表 | 128 |

> 判定为"合规"的代表性例子:`payment/service/impl/PaytranServiceImpl.java:371-383` 反射调用支付通道,`catch(InvocationTargetException)` 内 unwrap 后所有分支均以 `FLException(150072/150073)` 收尾——这是标准包装姿势,共 6 处同构代码全部合规。

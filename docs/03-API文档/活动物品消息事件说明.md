# 装修活动物品消息事件说明（information.messagecueuing）

> 版本：2026-10-29（commit 0401cec13 起生效）
> 生产表：`information.messagecueuing`（写方：ERP decoration/approval 模块；消费方：下游同步/额度治理）
> 关联：《优惠额度活动物品创建校验方案.md》《优惠额度活动物品创建校验部署说明.md》

---

## 一、表结构

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| mcid | bigint PK | 消息流水号 |
| orderid | varchar(15) | 装修单号（冗余列，便于按单检索） |
| operation | varchar(128) | 事件名（见第二节） |
| args | text | 事件参数 JSON（见第三节） |
| createtime | timestamp | 入队时间 |
| finishtime | timestamp | 消费完成时间（未消费=NULL） |
| status | tinyint | 0=未处理，1=已处理 |

写方为 `MessageQueuingDao.save(new MessageCueuingPO().init(orderId, operation, args))`，与业务操作**同事务**：业务回滚则消息随之消灭，消费方不会看到未发生的操作（无孤儿事件）。

## 二、事件清单（operation）

| operation | 触发动作（ERP 页面路径） | 数据来源 |
| --- | --- | --- |
| `addDecorationActivityItem` | ① 装修单详情 → 添加活动物品（直接添加路径）落行后；② 活动物品申领审批**通过**（approveForDecorationActivity）逐明细落行后，每个审批明细行各发一条 | `decorationactivityitem` 新行 |
| `abateDecorationActivityItem` | 活动物品**作废**（abateDecorationActivityItem，状态翻转 UNVALID 并回冲 couponCut/thingCut）后 | 被作废行 |
| `refundDecorationActivityItem` | 活动物品**退款**（refundDecorationActivityItem，状态翻转 RETREAT 并回库存回冲金额）后 | 被退款行 |

补充语义：

- **提交审批不产生事件**——`submitApprovalForDecorationActivity` 只写 `approvaldecorationactivityitem`（审批明细），不发消息；事件统一在审批**通过**建 `decorationactivityitem` 行时逐行发出。
- 本表对 `decorationactivityitem` **不存在物理 delete**：行的"移除"以 `abate`（作废）/`refund`（退款）两个状态翻转事件表达，消费方按事件语义自行扣减/恢复额度。
- 事件覆盖**全部类型**物品（券 0/物品 1/红包 2/优惠额度券 10/优惠额度物品 11/优惠额度红包 12），消费方如只关心额度类，可按 daiId 反查自身物品配置过滤。

## 三、args 契约

固定三参数，JSON 手拼，键序稳定：

```json
{"orderId":"2610210003","daiId":"3810","designerId":"FL-06189"}
```

| 键 | 类型 | 说明 |
| --- | --- | --- |
| orderId | string | 装修单号 |
| daiId | string | 装修活动物品行 id（`decorationactivityitem.daiId`，**字符串带引号**，对齐既有 consume 事件口径） |
| designerId | string | 装修单设计师工号（`decoration.designer.userId`）；**设计师为空时整个键缺省**（不出现该键），消费方须容忍无此键的报文 |

注意：报文里**不含物品类型/金额**，消费方需按 daiId 自行关联物品明细（ERP 侧行永不物理删除，daiId 恒可回查）。

## 四、消费约定

1. 拉取条件：`status=0 AND finishtime IS NULL`（与 ERP 侧 `queryMessageQueuing` 同口径），处理完置 `status=1` + `finishtime`。
2. 幂等：同一 daiId 理论上只会有一条 add 事件（行唯一），但消费方仍建议按 `(operation, daiId)` 幂等去重，防重放。
3. 顺序：add → abate/refund 可对同一 daiId 先后发生，消费方按 createtime/mcid 顺序应用。
4. 事件与业务同事务，但**跨事件不保证原子**（一次审批通过 N 行 = N 条独立 add 消息）。

## 五、对账/排障 SQL

```sql
-- 某单的事件轨迹
SELECT mcid, operation, args, createtime, finishtime, status
FROM information.messagecueuing
WHERE orderid = '2610210003' AND operation LIKE '%DecorationActivityItem%'
ORDER BY mcid;

-- 物品行轨迹对账（事件 vs 实表）
SELECT d.daiId, d.type, d.state, d.money, d.num, m.operation, m.createtime
FROM decoration.decorationactivityitem d
LEFT JOIN information.messagecueuing m ON m.args LIKE CONCAT('%"daiId":"', d.daiId, '"%')
WHERE d.orderId = '2610210003'
ORDER BY d.daiId, m.mcid;
```

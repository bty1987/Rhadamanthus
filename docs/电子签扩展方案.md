# 电子签扩展支持 e签宝（含多公司路由）方案

> 评估与改造计划。当前系统仅支持法大大电子签，本方案评估如何扩展支持 e签宝，并支持「不同公司选择不同电子签厂商」。
>
> 编写日期：2026-06-27

---

## 一、现状评估

### 1.1 现有架构（法大大）

```
业务方（9 处 ServiceImpl + 1 Action） ──静态直调──▶ Signature.java（约890行静态工具类）
                                                       │
                                                       ▼
                                          FddBaseClient / FddExtraClient / FddVerifyClient
                                                       │（fadada-api-sdk-1.7.17.1.jar）
                                                       ▼
                                                法大大 openapi
```

### 1.2 核心结论：直接耦合，缺乏厂商抽象层

| 维度 | 现状 | 是否阻碍扩展 |
|------|------|------------|
| SDK 调用层 | `Signature.java` 单一静态类，方法参数含法大大原生类型 | ✅ 阻碍 |
| 业务调用方 | 9 个 ServiceImpl + 1 Action 直接 `Signature.xxx()` 静态调用 | ✅ 阻碍 |
| 数据契约层 | `Contract`/`Signet` 接口（仅抽象 PO 字段） | ⚠️ 部分可复用 |
| 配置 | `conf/fadada.properties` + 静态块硬编码，全局单 appId | ✅ 阻碍（多公司路由） |
| 回调 | `FadadaCallback` 空壳，异步链路未跑通 | ⚠️ 既有缺陷 |
| 印章/签名管理 | `FadadaAction` 4 个接口 | ⚠️ 与厂商耦合 |
| 厂商标识 | `SignetPO.signno` / `CustomerPO.signno` / `UserPO.signNo` 均为裸字符串，不区分厂商（字段名统一用 `provider`） | ✅ 阻碍（多厂商并存） |

**有利点**：
- 业务 PO 已通过 `Contract`/`Signet` 接口被多业务复用（4 个 Contract PO + 2 个 Signet PO），「按业务隔离数据载体」的模式已建立，扩展多厂商只需在其上再加一层「厂商隔离」。
- **公司维度天然存在**：`SignetPO` / `ContractPO` / `SupplierSignetPO` / `DecorationPO` / `CustomerPO` / `UserPO` 都带 `company`/`cid` 字段，且印章/合同查询已按公司过滤，路由基础完备。
- **有先例可循**：`DingTalkApprovalConfigPO`（`hades.dingtalkapprovalconfig`）已证明「按 companyId 做差异化配置路由」的模式在项目中被采用。

**风险点**：
- `Signature.java` 错误码判断不统一（部分 `code==1`，部分 `"1000".equals(code)`），重构需保留原逻辑。
- 配置加密回退逻辑（`EncryptConfigLoader`）在静态块，迁移需小心。
- 客户/员工的 `signno` 是单值字段，无法表达「属于哪家厂商」，多厂商并存需扩展。

## 二、改造目标与原则

1. **保持现有功能不变**：法大大链路行为 100% 等价，不引入回归。
2. **最小侵入业务方**：业务 ServiceImpl 只改「如何拿到签名服务」，不改业务流程。
3. **新增而非重写**：法大大实现保留为 `FadadaElecsignService`，e签宝新增 `ESignElecsignService`。
4. **可配置切换 + 多公司路由**：支持全局切换厂商，支持「不同公司用不同厂商」，预留按业务/合同类型细粒度路由。
5. **先内后外**：先抽象后接入 e签宝，分阶段灰度，每阶段可独立验证、可回滚。

## 三、目标架构

```
┌──────────────────────────────────────────────────────────────┐
│  业务层：CustomerServiceImpl / SignetServiceImpl /            │
│          DecorationContractServiceImpl ... (9处+1Action)      │
│     只依赖 ElecsignService 接口（@Autowired）           │
└───────────────────────────┬──────────────────────────────────┘
                            ▼ 注入的是 Router，非单一实现
┌──────────────────────────────────────────────────────────────┐
│     ElecsignRouter / 工厂                              │
│     按 company（→ provider）路由到对应实现                    │
│     company=总部 → fadada；company=某分公司 → esign           │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────┬───────────────────────────────────────┤
│  配置层：            │  company_esign_config 表（新建）       │
│  companyId → provider│  cid | companyId | provider | appId |  │
│  + appId + secret    │  secret | host | enabled                │
└──────────┬───────────┴───────────────────────────────────────┘
           ▼ 路由结果
┌──────────────────────┐              ┌────────────────────────┐
│ FadadaElectronic     │              │ ESignElectronic        │
│ SignService          │              │ SignService            │
│ (现 Signature.java   │              │ (新实现，调 e签宝 SDK) │
│  改造)               │              │                        │
└──────────┬───────────┘              └───────────┬────────────┘
           ▼                                       ▼
    法大大 SDK                               e签宝 SDK
```

### 3.1 路由策略：三档可选

| 方案 | 粒度 | 复杂度 | 适用场景 |
|------|------|--------|---------|
| **A. 全局单厂商** | 整个系统一种厂商 | 低 | 全公司统一切换 |
| **B. 按公司路由（推荐）** | 不同公司不同厂商 | 中 | 总部法大大、某分公司 e签宝 |
| **C. 按合同类型路由** | 同一公司内不同业务不同厂商 | 高 | 装饰走 A、付款走 B |

> **本期推荐落地 A + B**：默认 A（全局法大大），B 作为正式能力（按公司路由）。C 预留扩展点，本期不实现。
>
> A 与 B 可以平滑演进：无 `company_esign_config` 记录的公司走全局默认厂商，有记录的公司按配置走。这样初期不配任何记录即等价于现状（全局法大大）。

### 阶段 1：抽象统一服务接口（核心，1.5 天）

新建包 `com.fanglin.esign`（电子签通用层，名字中立，避免与 `fadada` 包混淆）：

```
com.fanglin.esign/
├── service/
│   ├── ElecsignService.java        # 统一接口
│   ├── ElecsignProvider.java       # 厂商标记枚举 FADADA/ESIGN
│   └── ElecsignContext.java        # 调用上下文（含 companyId/provider/credentials）
├── dto/                                  # 厂商中立入参/出参（避免 SDK 类型外泄）
│   ├── RegisterRequest.java
│   ├── AuthenticateRequest.java
│   ├── GenerateContractRequest.java
│   ├── SignRequest.java                  # 含签署方式：关键字/坐标
│   ├── ExtSignRequest.java               # 手动签署（返回签署URL）
│   ├── ContractResult.java               # 含 viewUrl/downloadUrl/status
│   └── SignResult.java
└── exception/
    └── ElecsignException.java      # 统一异常，包装厂商错误码
```

`ElecsignService` 方法清单（对齐现 `Signature.java`，保证业务方零语义改动）：

```java
public interface ElecsignService {
    // —— 实名认证 ——
    SignResult register(Signet signet);
    String authenticate(Signet signet);                    // 返回认证URL
    CertResult companyCert(Signet signet);
    CertResult personCert(String signno);
    void applyCertificate(String signno, String token);
    void beforeAutoSign(Signet signet);

    // —— 合同 ——
    void uploadTemplate(String templateId, ...);
    void generate(Contract contract, String json, List<Object> tables);
    void upload(Contract contract, String path);
    SignResult autoSign(String signno, Contract contract, ...);
    String extSign(String signno, Contract contract);      // 返回手动签署URL
    String view(Contract contract);
    String download(Contract contract);
    void filing(Contract contract);

    // —— 印章/签名 ——
    Object querySignature(SignatureVO vo);
    void addSignature(SignatureVO vo);
    void defaultSignature(SignatureVO vo);
    void deleteSignature(SignatureVO vo);
}
```

**关键决策**：
- DTO 用项目自定义类型（如 `GenerateContractRequest`），**不暴露** 法大大的 `ExtSignAutoParams`，否则切换无意义。
- 异常统一为 `ElecsignException`，各实现负责把厂商错误码翻译成统一文案（保留原 code 供排查）。
- 方法支持接收 `ElecsignContext`（含 companyId + 该公司的凭证），为多公司路由铺路。

**交付**：`com.fanglin.esign` 接口与 DTO，编译通过（尚无实现）。

### 阶段 2：法大大实现下沉（1.5 天）

1. 新建 `com.fanglin.fadada.service.impl.FadadaElecsignServiceImpl implements ElecsignService`。
2. 每个接口方法内部转调原 `Signature.xxx()`（**原 `Signature.java` 保留不动**，作为底层 SDK 封装继续存在），入参用 DTO → 拆出原参数 → 调静态方法。
3. 错误码处理完全照搬 `Signature.java` 现有判断逻辑（`code==1` / `"1000"`），不重构、不统一，保证等价。
4. 配置：`FadadaElecsignServiceImpl` 通过 `EncryptConfigLoader` 读取 `fadada.properties`（保持现状）。

**验证**：实现写完后单元自测每个方法的入参适配。

**交付**：`FadadaElecsignServiceImpl`，法大大能力无损下沉。

### 阶段 3：业务方切换为接口依赖（关键，1 天）

**目标**：9 处 `Signature.xxx()` 静态调用 → `@Autowired ElecsignService`（先注入单一实现，阶段 4 再换 Router）。

**改动范围**（仅改「如何获取服务」，不改业务流程）：

| 业务 ServiceImpl | 调用方法 |
|------------------|---------|
| `communion...CustomerServiceImpl` | register/authenticate/person/signature |
| `personel...UserServiceImpl` | register/authenticate/person/signature |
| `data...SignetServiceImpl` | register/authenticate/company/signature/beforeauto |
| `data...SupplierSignetServiceImpl` | 同上 |
| `data...ContractServiceImpl` | template |
| `decoration...DecorationContractServiceImpl` | view/extsign/generate/autosign/filing |
| `personel...UserContractServiceImpl` | extsign/view/autosign/generate |
| `personel...SupplierContractServiceImpl` | view/autosign/extsign/generate |
| `payment...PaymentContractServiceImpl` | extsign/view/autosign/upload/filing |
| `data/action...FadadaAction` | pollingSignature/addSignature/... |

**步骤**：
1. 每个 ServiceImpl 加 `@Autowired private ElecsignService elecsignService;`
2. IDE 批量替换 `Signature.xxx(` → `elecsignService.xxx(`，逐个核对入参 DTO 适配。
3. `FadadaAction` 同样改注入。

**验证（回归门）**：完成此阶段后**法大大全链路回归必须通过**，证明抽象无损。这是最重要的安全网。

**交付**：业务方全部解耦，`Signature` 不再被业务直接引用（仅 `FadadaElecsignServiceImpl` 内部用）。

### 阶段 4：配置隔离与多公司路由（核心，1 天）

#### 4.1 复用 communion.systemconfig（不建新表）

经评估，电子签厂商配置是低频运维操作（一家公司配一次），无需独立表。直接复用项目既有的
`communion.systemconfig`（key/value/company 结构，天然支持按公司配置，已有管理页面）。

配置约定（`group=elecsign`）：

| group | key | value | company | 说明 |
|-------|-----|-------|---------|------|
| elecsign | `elecsign.default.provider` | `fadada` | 0 | 全局默认厂商（company=0 表全局） |
| elecsign | `elecsign.provider` | `esign` | {cid} | 某公司用 e签宝 |
| elecsign | `elecsign.appId` | `xxx` | {cid} | 该公司 e签宝 appId |
| elecsign | `elecsign.appSecret` | `xxx`(加密) | {cid} | 该公司 e签宝密钥 |
| elecsign | `elecsign.host` | `https://...` | {cid} | 可选，openapi 地址 |

> 相比建独立表：零 DDL、零新 PO/DAO/Service、复用现有管理页面、查询用现成 `SystemConfigDao.querySystemConfig(key, company)`。

#### 4.2 路由器 ElecsignRouter

```java
@Component
public class ElecsignRouter {
    @Autowired private Map<String, ElecsignService> impls;   // Spring 注入所有实现
    @Autowired private SystemConfigDao systemConfigDao;

    // 路由优先级：公司级 elecsign.provider → 全局 elecsign.default.provider → 硬兜底法大大
    public ElecsignProvider resolveProvider(int companyId) { ... }
    public ElecsignService route(int companyId) { return route(resolveProvider(companyId)); }
    public ElecsignService route(ElecsignProvider provider) { ... } // 按数据自身记录的厂商
}
```

路由优先级（`resolveProvider`）：
1. 查该公司 `elecsign.provider`（`systemConfigDao.querySystemConfig(key, companyId)`）→ 有则用
2. 查全局 `elecsign.default.provider`（company=0）→ 有则用
3. 都没有 → 硬兜底 `FADADA`（等价现状）

业务方（阶段6c）注入 `ElecsignRouter`，调用 `router.route(companyId).xxx(...)`。
`companyId` 来源：印章/合同/客户/员工 PO 上本就有 `company` 字段，直接取。

#### 4.3 Spring 装配

`conf/ApplicationContext.xml`：
```xml
<bean id="fadadaElecsignService" class="com.fanglin.fadada.service.impl.FadadaElecsignServiceImpl"/>
<!-- 阶段5 新增 esignElecsignService -->
```

**验证**：法大大回归仍通过（此时 Router 只会路由到 fadada）。

**交付**：可配置、可按公司路由的装配机制。

### 阶段 5：e签宝实现接入（2-3 天）

1. 引入 e签宝 SDK：放 `WebContent/WEB-INF/lib/` 与 `project-libs/`，更新 `.classpath`。
2. 在 `systemconfig` 表为使用 e签宝的公司插入一组配置（elecsign.provider=esign + appId + appSecret）。
3. 新建 `com.fanglin.esign.service.impl.ESignElecsignServiceImpl implements ElecsignService`：
   - 每个方法调用 e签宝 SDK，能力映射见 §六。
   - 印章/签名管理若 e签宝 API 差异大，先实现「够用子集」，其余抛 `UnsupportedOperation` 并记 TODO。
4. 回调：新建 `ESignCallback`，**顺带补齐** `FadadaCallback` 空壳（既有缺陷）。
5. `ApplicationContext.xml` 增加 e签宝 bean，Router 自动发现。

**验证**：e签宝环境跑通客户认证 + 一类合同全流程（建议先装饰合同）。

**交付**：`ESignElecsignServiceImpl` + 回调。

### 阶段 6：数据模型扩展——厂商标识（1 天）

多厂商并存时，`SignetPO.signno` / `CustomerPO.signno` / `UserPO.signNo` 需区分归属厂商，否则切换公司路由后无法识别历史账号。

**方案**：为这三张表各加一个 `provider`（TINYINT，1=法大大，2=e签宝），**不删改现有 signno 列**，存量数据全量刷为 1（法大大）。

```sql
ALTER TABLE data.signet         ADD COLUMN provider TINYINT NOT NULL DEFAULT 1;
ALTER TABLE communion.customer  ADD COLUMN provider TINYINT NOT NULL DEFAULT 1;
ALTER TABLE communion.user      ADD COLUMN provider TINYINT NOT NULL DEFAULT 1;
-- supplierSignet 同理
```

- 历史数据：`UPDATE ... SET provider = 1;`
- 新注册流程：`register()` 时按当前路由厂商写入 `provider`。
- 查询签署账号时：必须 `WHERE signno = ? AND provider = ?`，避免跨厂商串号。

**合同模型兼容**：e签宝用 `fileId/flowId`，法大大用 `contractId`。建议在 `Contract` 接口加可选字段 `thirdPartyContractId`，各厂商实现各自取用，**不破坏** 现有 PO 表结构（新列 nullable）。

**交付**：兼容两家厂商的数据模型调整 + 数据迁移脚本。

### 阶段 6c：业务方切换到 ElecsignRouter（⚠️ 推迟到阶段 5 就绪后）

**状态：已完成可行性调研，结论是推迟到阶段 5 e签宝实现就绪后一次性做。**

#### 调研结论：44 个调用点的 company 来源分布

| 类别 | 数量 | 说明 |
|------|:---:|------|
| ✅ 方法体内已有 PO 带 company | 26 处 | SignetServiceImpl/CustomerServiceImpl/UserServiceImpl/FadadaAction 等，直接 `.getCompany()` |
| ⚠️ 补一次查询可拿到 | 14 处 | 合同类方法有 orderId/uid，补查一次 DecorationPO/UserPO 即可 |
| ❌ 拿不到 | 2 处 | `SupplierContractServiceImpl.viewSupplierContract/makeSupplierContract`，供应商域整体无 company 字段，需改方法签名或加列 |

#### 推迟理由

1. **当前切 Router 零收益**：e签宝实现不存在，Router 100% 路由到法大大，等于改了 44 处却验证不了路由逻辑
2. **14 处补查询是纯开销**：切 Router 前这些 `decorationDao.queryDecorationByOrderId()` 查询完全不需要，提前加只是增加当前风险
3. **2 处无论如何得等阶段 5**：6c 做了也不完整
4. **回归风险大**：44 处调用方式全变，每处须正确传 companyId（如 SupplierSignet 的临时 signetPO 要补 set company），传错即 bug

#### 建议执行时机

阶段 5 e签宝实现就绪后，一次性做 6c：
- 那时有多厂商场景，Router 路由可端到端验证
- 补的查询真正有用（用于区分走哪家厂商）
- 2 处拿不到 company 的可一并改造

> **当前阶段（1-4 + 6a + 6b）已完成的等价保证**：业务方直接注入 `ElecsignService`（当前唯一实现是法大大），
> 行为与改造前 100% 等价。Router 已就绪但未被业务方调用，等阶段 5 后激活。

**交付**：上线方案 + 回滚预案。

## 六、法大大 ↔ e签宝 能力映射（预研要点）

| 能力 | 法大大 | e签宝对应 | 风险 |
|------|--------|----------|------|
| 注册账号 | `invokeRegisterAccount` | 账户注册 / 组织机构创建 | 字段映射差异 |
| 企业实名 | `invokeCompanyVerifyUrl` | 企业实名认证（返回 H5/扫码） | 认证流程不同 |
| 个人实名 | `invokePersonVerifyUrl` | 个人实名认证 | 同上 |
| 模板合同 | `invokeUploadTemplate`+`generateContract` | 模板管理 + 基于模板创建文件 | **模板变量语法不同，需重做模板** |
| 上传 PDF | `invokeUploadDocs` | 文件上传 | OK |
| 自动签 | `invokeExtSignAuto` | 一步到位签署 / 静默签 | 拓展项配置差异大 |
| 手动签 | `invokeExtSign`（返回URL） | 签署流程创建 + 获取签署链接 | e签宝用 flow 模型，多一步 |
| 预览/下载 | `viewPdf`/`downloadPdf` | 文件预览 / 文件下载 | OK |
| 归档 | `invokeContractFilling` | 流程归档 | OK |
| 印章管理 | `querySignature` 等 | 印章管理 API | 模型差异较大，可能需重做 |

**重点**：合同模板的变量占位语法两家不兼容，**现有模板无法直接复用**，需在 e签宝平台重新制作并维护一套对应模板（业务侧 `templateId` 需配置化区分厂商，建议 `ContractPO` 加 `templateIdFadada` / `templateIdEsign` 两列，或新建 `contract_template_esign` 子表）。

## 七、多公司路由专项说明

### 7.1 可行性结论

**完全可行**，理由：
1. 公司维度天然存在：`SignetPO` / `ContractPO` / `DecorationPO` / `CustomerPO` / `UserPO` 均带 `company` 字段，且查询已按公司过滤。
2. 既有先例：`DingTalkApprovalConfigPO` 已按 `companyId` 做差异化配置路由。
3. 凭证隔离方案清晰：复用 `systemconfig`，按公司 key 配 appId/secret/provider。

### 7.2 注意事项

| 场景 | 处理 |
|------|------|
| 同一客户跨公司签署 | 现 `CustomerPO.signno` 单值绑定一个 `company`。若需同一人在不同公司用不同厂商，需改为 `(customerId, company)` 联合维度存多份，或限制单客户单厂商。**建议本期限制：一个客户在同一公司内只用一种厂商**，跨公司各存各的 signno。 |
| 公司切换厂商 | 历史合同仍用原厂商账号；新合同走新厂商。`provider` 字段保证历史账号可识别。需在 `sign`/`view`/`download` 时按合同记录的 `provider` 路由，而非公司当前配置。 |
| 印章 `SignetPO` | 按公司+厂商隔离，天然支持（每家公司每家厂商一套 signno/signid）。 |
| 全局默认 | 无 `elecsign.provider` 公司配置的走 `elecsign.default.provider`，初期等价现状。 |

### 7.3 路由优先级

合同/印章的 `provider` 字段（数据本身记录的厂商） **优先于** 公司当前配置：
- 已存在的合同/印章 → 按 `provider` 路由（保证历史数据可继续查看/下载）。
- 新建合同/印章 → 按公司当前 `elecsign.provider` 配置路由，并写入本次记录的 `provider`。

这样即使公司中途切换厂商，历史数据不丢失、可回溯。

## 八、风险与对策

| 风险 | 对策 |
|------|------|
| `Signature.java` 错误码判断不一致（`1` vs `1000`） | 下沉时照搬，不重构；e签宝实现独立写映射 |
| 配置加密回退逻辑在静态块 | `FadadaElecsignServiceImpl` 保留原加载方式，不动 |
| e签宝 SDK 与现有加密库版本冲突 | 阶段 0 先用 `mvn dependency:tree` 核对 |
| 合同模板不能复用 | 模板 ID 配置化，按厂商维护 |
| 回调链路本就未跑通 | 借此次改造一并补齐两家回调 |
| 静态调用面广（9处Service+1 Action） | 阶段 3 IDE 批量替换 + 全量回归门把关 |
| 多厂商并存导致 signno 串号 | 加 `provider` 字段，查询带厂商条件 |
| 公司切换厂商后历史合同不可用 | 路由按合同记录的 `provider`，而非公司当前配置 |

## 九、建议

1. **优先落阶段 0-4**（约 6 人日）：这部分即使不接 e签宝，也完成了「消除静态耦合、统一接口、多公司路由能力」的重构，风险低、价值独立。建议作为独立 refactor commit 先合入。
2. **阶段 5-7 再视 e签宝商务决策推进**，技术上已被前置重构铺平。
3. **多公司路由**建议作为正式能力（方案 B），而非临时方案：即使初期全用法大大，配置表预留好后，未来任何分公司切 e签宝 只需加一行配置 + 该分公司重新做模板，零代码改动。

## 二、四类问题的本质与处置建议

### 2.1 代码内漂移(113 个)—— 最严重,核心问题

**本质**:一个错误码在代码里有多种消息文本。前端收到的 `errorMsg` 取决于触发了哪个 throw 点,**完全不可预测**。

**进一步分类**:

| 子类 | 数量 | 典型 | 处置 |
|---|---|---|---|
| 占位/笔误码 | 1 | `000000`(假期/银行账户) | 改用正规码 |
| 正常码段复用 | 112 | `130002` 同时是客户/合同不存在 | 见下 |

正常码段复用中,**39 个码有 3+ 种消息**(严重复用),典型:

| 码 | 消息种数 | 消息示例 |
|---|---|---|
| `190005` | 6 | 业务员/人员/厂商/员工不存在、用户工号不能为空、用户未关联部门 |
| `240010` | 5 | 审批任务已处理/未指派审批人/无权审批/转交目标不能为空 |
| `110008` | 4 | 验证信息错误 1/2/3 |
| `140013` | 4 | 订单/装修单/装修订单不存在(含一个带 Tab 缩进的脏数据) |

**根因**:开发者把一个码当"一类错误"的通用标识跨模块复用,而非为每个独立语义分配独立码。

**对第二档的影响**:**致命**。第二档要做"码→消息"的 1:1 映射(error-cn.json 里每个码一个消息),但现有 113 个码是 1:N。直接按现状生成目录,会有 113 个码的消息无法确定。

**处置**:第二档常量枚举设计时,**必须为每个"码+语义"拆分独立码**。例如 `190005` 要拆成 `EMPLOYEE_NOT_EXIST`(人员不存在)、`SUPPLIER_NOT_EXIST`(厂商不存在)、`USER_NO_DEPT`(用户未关联部门)等多个枚举值,分配不同的码。

---

### 2.2 未登记码(72 个)—— magic number 泛滥

**本质**:代码里用了 error.md 没有的码。

典型:
- `000000` 占位码(银行账户/假期)
- `10000` 余额不足(应是 150010)
- `37002` 外销付款不存在(应是 370026)
- `110023/110027/110030` 等码段外码
- `400001-400005` 一批新码(可能是 seiya 新增接口未登记)
- `240050/240052/240060/240070` approval 模块新码未登记

**根因**:无强制流程约束,新增码不登记文档。

**处置**:① 短期——人工核对 72 个码,该登记的登记、该改的改(如 `10000`→`150010`)。② 长期——第二档构建期三向校验,新码未登记则构建失败。

---

### 2.3 死码(173 个)—— 文档冗余

**本质**:error.md 有登记但代码完全没用。

注意:其中 `-3/-2/-1/0` 是特殊语义码(成功/无权限/数据冲突),在拦截器里以字符串 `"-2"` 形式使用,脚本正则只抓数字 `FLException(code`,所以误报为"未使用"。剔除这 4 个,真实死码约 **169 个**。

**典型**:`120002-120012` 一连串"当前订单X款"消息、`130019` 房产已存在 等。

**根因**:业务演进中废弃的码未从文档删除(第一档已将空位标 reserved,但这些是"有消息但不用"的码)。

**处置**:① 人工确认 169 个死码确实无用后,消息列改为 `deprecated` 或直接删除回收。② 第二档构建期校验:文档有但代码+常量类都没有的码,标记警告。

---

### 2.4 文档滞后(51 个)—— 文档与代码措辞不符

**本质**:码在用、文档也在,但文档消息和代码消息对不上。

典型:
- `110019` 文档"日期格式问题",代码"用户ID不能为空" —— 完全不同的语义被塞进同一码
- `230002` 文档"城市已被引用",代码"已停用的账户不能设为默认" —— 跨业务复用导致
- `130101` 文档"话术不存在(ChatingService用)",代码"话术不存在" —— 第一档加的注释导致比对不符(可忽略)

**根因**:文档更新滞后于代码,或码被跨业务复用后文档没同步。

**处置**:① 逐个核对 51 个码,以代码为准更新文档(或反之)。② 第二档后文档从 JSON 派生,这类问题自动消解。

## 三、对第二档的关键启示

诊断结果对第二档设计有直接约束:

### 3.1 不能直接按现有码生成 error-cn.json

113 个码是 1:N(一码多义),直接生成目录会有 113 个码的消息无法确定。第二档必须:

```
现状: 码 190005 → 6种消息(业务员/人员/厂商/员工不存在...)
                ↓ 拆码
目标: 190005 → 人员不存在(保留主语义)
      19xxxx → 业务员不存在(新码)
      19xxxx → 厂商不存在(新码)
      ...
```

### 3.2 常量枚举要先于目录设计

不能先做 error-cn.json 再做枚举,顺序应反过来:
1. 先把 113 个漂移码拆分成"码+语义"的独立单元
2. 为每个单元分配码(复用旧码或申请新码)
3. 再生成 error-cn.json(此时每个码唯一消息)
4. 最后构建期三向校验

### 3.3 拆码工作量评估

113 个漂移码,39 个严重(3+ 消息)。按每个漂移码平均拆出 2-3 个独立码估算,第二档需要新增约 150-200 个码,并迁移相应 throw 点。这远超"渐进迁移"的单模块范围,**需要专项规划**。

## 五、脚本使用

```bash
# 全量诊断
python scripts/check_errorcode_consistency.py

# 导出 CSV 明细
python scripts/check_errorcode_consistency.py --csv scripts/output/errorcode_diff.csv
```

脚本可重复运行,作为第二档推进过程中的回归基线:每修复一类问题,重跑脚本观察问题数下降。
